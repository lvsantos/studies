Instalar o Spec Kit sem misturar as duas etapas

Vitória de hoje: deixar o comando specify disponível e saber quando inicializar um projeto.

A ideia central

Spec Kit tem dois momentos diferentes:

  1. Instalar o CLI: instala o pacote specify-cli uma vez no seu ambiente.
  2. Inicializar um projeto: usa specify init para criar a estrutura e a integração do agente naquele projeto.

1. Instale e verifique

Com Python 3.11+ e uv disponíveis:

uv tool install specify-cli
specify version

Se o segundo comando mostrar uma versão, a instalação do CLI terminou. A documentação oficial também descreve pipx install specify-cli como alternativa.

Se aparecer “Executable already exists: specify”

Esse aviso significa que já existe um executável specify no seu ambiente. Não é necessário reinstalar para continuar: execute:

specify version

Se o comando mostrar o quadro Specify CLI Information e uma versão, o CLI já está instalado e funcionando. Só use --force se você realmente quiser substituir a instalação existente.

Como saber se está atualizado

specify version mostra apenas a versão instalada. Para consultar se existe uma versão mais nova, use o comando somente leitura:

specify self check

O resultado informa Up to date quando não há atualização ou mostra algo como Update available: versão-atual → versão-nova quando há uma versão disponível.

Para visualizar o plano de atualização sem alterar nada:

specify self upgrade --dry-run

Para instalar a versão estável mais recente:

specify self upgrade

Depois, confirme novamente com specify version. O comando self upgrade identifica se a instalação foi feita com uv ou pipx.

Solução de problemas: “Verification failed” ou PATH incorreto (VS Code Snap)

Se após o specify self upgrade você receber o aviso de que o diretório não está no PATH (ex: ~/snap/code/.../.local/bin) e a versão continuar antiga no terminal, isso ocorre porque o VS Code rodando via Snap instala os binários no diretório de sandbox do Snap, enquanto seu terminal prioriza ~/.local/bin.

Para resolver e forçar a instalação no diretório padrão do usuário (~/.local/bin), defina a versão do Spec Kit que você quer instalar. O valor 1.0.8 abaixo é apenas um exemplo: substitua-o pela versão desejada antes de executar:

SPEC_KIT_VERSION=1.0.8
  UV_TOOL_BIN_DIR=$HOME/.local/bin uv tool install specify-cli --force --from git+https://github.com/github/spec-kit.git@v$SPEC_KIT_VERSION

Ou para versões estáveis do PyPI:

UV_TOOL_BIN_DIR=$HOME/.local/bin uv tool install specify-cli --force

Em seguida, execute specify version para confirmar a versão atualizada.

2. Inicialize para o Copilot

Para criar um novo diretório:

specify init meu-projeto --integration copilot

Para usar a pasta atual:

specify init --here --integration copilot

Adotando o Spec Kit em um projeto existente

Em repositórios já existentes e não vazios, execute o comando especificando a integração do seu agente (ex: copilot):

specify init --here --force --integration copilot
Cuidados fundamentais com o --force:
  • Crie uma linha de base (baseline) no Git: Faça commit ou stash de todas as alterações antes de executar o comando e crie uma nova branch para a adoção. Isso garante que cada arquivo gerado pelo Spec Kit fique visível no git diff.
  • O que o --force faz: Permite inicializar em pastas com arquivos existentes e pode sobrescrever arquivos conflitantes apenas em caminhos gerenciados pelo Spec Kit (como a pasta .specify/ e arquivos de skills/instruções do agente). Ele não apaga nem reescreve o código da sua aplicação.
  • Revise o git diff imediatamente: Após rodar o comando, inspecione a diferença de arquivos para confirmar a inclusão dos arquivos de integração do Copilot e da estrutura .specify/.
  • Não cria especificações retroativas: O Spec Kit não analisa ou reescreve o comportamento antigo do seu sistema; ele apenas estabelece o ambiente para a próxima mudança delimitada.
Dicas para os Project Guardrails (Constituição):

Defina as regras e restrições fundamentais do repositório executando /speckit.constitution:

  • Evidências reais do repositório: Use o README.md, guias de contribuição (CONTRIBUTING.md), registros de arquitetura (ADRs) e configurações de CI como evidência. Não invente padrões apenas para preencher o modelo.
  • Evite regras irrealistas: A constituição orienta análises e planejamentos futuros. Regras inventadas ou irrealistas geram ruído em vez de restrições úteis.
  • Acelere a geração com o Copilot: Peça ao agente para ler seu README e pipeline de CI atual para propor os rascunhos dos guardrails inegociáveis (ex: suíte de testes obrigatória, compatibilidade de APIs e rollback em migrations).
  • Mantenha os princípios verificáveis: Escolha regras concisas que a IA e os revisores consigam validar objetivamente durante o `git diff`.

Nota: teremos uma lição dedicada e aprofundada sobre a construção da Constituição do Projeto no futuro.
