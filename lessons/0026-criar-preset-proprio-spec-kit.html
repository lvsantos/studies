Do scaffold ao seu primeiro preset

Vitória de hoje: transformar uma regra recorrente da equipe em um pacote instalável, testar se ela realmente afeta o artefato e saber quando o scaffold oficial economiza trabalho.

O exemplo da aula

Uma equipe quer que todo plano de feature registre riscos de segurança e uma mitigação. Vamos acrescentar essa seção ao fim do template de plano. Como a regra muda a estrutura do documento, começaremos com um template, sem substituir nem reescrever o comando central.

Um preset é adequado porque adapta um processo existente. Se a regra exigisse executar um scanner, abrir um ticket ou introduzir uma nova etapa automática, o próximo candidato seria uma extensão.

1. Defina a regra antes dos arquivos

Escreva uma frase que permita testar o resultado: “Todo plano deve terminar com uma revisão de segurança que liste riscos, mitigação e itens não aplicáveis com justificativa.” Essa frase determina o que o preset fornece e como vamos verificar que funcionou.

  1. É repetível entre projetos? Se só vale para um repositório, use um override local.
  2. O Spec Kit já executa o processo? Se sim e você quer mudar formato ou instruções, use um preset.
  3. Precisa de capacidade ou integração nova? Isso aponta para uma extensão, não para um preset.

A decisão oficial de customização separa essas opções pelo trabalho que a mudança realiza, não pelo tamanho do pacote.

2. O que o scaffold oferece

O scaffold oficial é um diretório de partida, não um preset de produto pronto chamado scaffold. Seu manifest começa com o ID my-preset. Você copia a pasta, troca os metadados e mantém apenas os arquivos que fazem sentido.

Pesquisar o formato do manifest, os caminhos e os nomes resolvidos.Partir de um preset.yml comentado e uma estrutura já reconhecida.

O molde traz exemplos ilustrativos ligados a uma extensão chamada myext. Eles não significam que essa extensão esteja instalada: remova as entradas e os arquivos que não fazem parte do seu caso. O scaffold economiza estrutura e sintaxe; não substitui o desenho da regra, os testes ou a revisão.

3. Copie e dê identidade ao pacote

Faça isso a partir do checkout do repositório oficial. O projeto em que você instalar o preset para testá-lo precisa já ter sido iniciado com specify init.

cp -r presets/scaffold security-review
# Edite security-review/preset.yml e remova os exemplos que nao usara
# Edite ou crie os arquivos em security-review/templates/ e commands/

Troque o ID my-preset por um ID único em minúsculas e hífens, por exemplo security-review. Atualize nome, descrição, versão semântica, autor, repositório, licença, versão mínima do Spec Kit e tags. O ID do manifest é o que será usado para remover o preset; ele não precisa ser igual ao nome da pasta.

4. Declare o template no manifest

Para uma seção adicional, a estratégia append preserva o template de plano de menor prioridade e acrescenta o arquivo do preset ao final. O exemplo abaixo mostra os metadados relevantes e uma única entrada em provides.templates:

schema_version: "1.0"

preset:
  id: "security-review"
  name: "Security Review"
  version: "0.1.0"
  description: "Adds a security review to feature plans"
  author: "Your Team"
  repository: "https://github.com/your-org/security-review"
  license: "MIT"

requires:
  speckit_version: ">=0.1.0"

provides:
  templates:
    - type: "template"
      name: "plan-template"
      file: "templates/plan-security-addendum.md"
      description: "Appends security review prompts to plans"
      replaces: "plan-template"
      strategy: "append"

tags:
  - "security"
  - "planning"

name identifica o item na pilha de resolução; file aponta para o conteúdo que vamos criar; replaces documenta o template afetado; e strategy escolhe a composição. Em replace, o arquivo substituiria todo o plano. Aqui escolhemos append para preservar as seções centrais. Os tipos de item, campos e marcadores são detalhados no manifest de exemplo.

5. Escreva o conteúdo e mantenha o escopo pequeno

Crie security-review/templates/plan-security-addendum.md com a parte reutilizável da regra. Um template precisa dar forma à saída e deixar claro o que o agente deve preencher:

## Security Review

For each relevant risk, record the affected asset or boundary,
the threat, and a mitigation or verification step.

| Risk or asset | Threat | Mitigation or verification |
|---------------|--------|----------------------------|
| [Fill in]     | [Fill in] | [Fill in] |

If no security-relevant change is identified, explain why this
review is not applicable.

Por enquanto, não crie um override de speckit.plan: o ganho esperado é apenas uma seção consistente no artefato. Adicione um comando ao preset somente se o agente precisar de instruções de trabalho diferentes que o template, sozinho, não consegue expressar.

6. Instale em desenvolvimento e teste o efeito

Em um projeto de laboratório inicializado com Spec Kit, execute:

specify preset add --dev ./caminho/para/security-review
specify preset list
specify preset resolve plan-template

Confirme que o preset aparece na lista e que resolve mostra o arquivo aditivo na pilha. Depois peça ao agente ativo que gere ou atualize um plano real e confira três coisas:

  1. A seção Security Review aparece no plano final.
  2. As seções centrais do plano continuam presentes.
  3. Quando não há risco relevante, há uma justificativa, não um campo silenciosamente vazio.

Se a seção não aparecer, confira primeiro o nome resolvido, a presença do arquivo indicado em file e o uso de append. Se resolve aponta para o preset mas o plano gerado não tem a seção, investigue se o agente usou o comando/template efetivo esperado. Ao terminar o teste:

specify preset remove security-review

Essa verificação é o teste que decide a hipótese da aula: se o template aditivo aparecer e sobreviver no plano gerado, não foi necessário criar um comando próprio para esta regra. O comando --dev serve para experimentar a pasta local; não é publicação nem validação completa do pacote.

7. Quando estiver pronto para compartilhar

Antes de publicar, faça o pacote caber no que ele promete: retire exemplos alheios, revise se todos os arquivos declarados existem e registre apenas os templates/comandos realmente fornecidos. Escreva um README.md específico para o preset, inclua uma licença e explique o uso, os casos adequados e as limitações. Versione em SemVer e teste de novo com --dev.

O guia oficial de publicação cobre release, README com comando de instalação e submissão ao catálogo da comunidade. A entrada no catálogo ajuda na descoberta; não é uma auditoria de segurança do código do preset.

8. Pratique: template ou comando?

O preset já acrescenta a seção de segurança, mas o time agora exige que o agente sempre consulte uma política interna e registre como essa política afetou o plano. O que você investigaria primeiro: mudar apenas o template, adicionar instruções ao comando, ou criar uma extensão? Responda antes de revelar.

Provavelmente ajustar o comando do fluxo de plano, se a consulta à política for uma instrução que o agente consegue seguir com os arquivos disponíveis. O template pode reservar lugar para a conclusão, mas não garante que o agente consulte a fonte. Se a consulta precisar de automação, credenciais ou integração externa, desenhe uma extensão. Teste primeiro a opção menor.
