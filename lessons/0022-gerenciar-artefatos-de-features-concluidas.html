Uma feature terminou. E agora, o que fazer com a spec?

Vitória de hoje: parar de deixar essa decisão acontecer por acidente e escolher, de propósito, um modelo de persistência para spec.md, plan.md e tasks.md.

O mapa mental

Existem duas perguntas independentes. A primeira é filosófica: por quanto tempo uma spec deveria importar? A segunda é operacional: quando os requisitos mudam, o que acontece com os arquivos que já existem?

A lição 3 apresentou os caminhos e comandos até /speckit-converge. Esta lição cobre o que ninguém pergunta: o dia seguinte ao converge.

1. A pergunta filosófica: os três níveis de SDD

Birgitta Böckeler (Thoughtworks), no artigo Understanding Spec-Driven-Development, observa que "spec-driven development" esconde três compromissos bem diferentes:

NívelCompromisso
Spec-firstA spec existe só para guiar a codificação. Depois, pode ser esquecida.
Spec-anchoredA spec sobrevive à implementação e é usada de novo quando a feature evolui.
Spec-as-sourceA spec é a única coisa editada por humanos; o código é gerado a partir dela.

A autora nota algo importante sobre o Spec Kit especificamente: ele cria uma pasta nova por spec e (com a extensão de git) um branch por mudança — um sinal de que, por padrão, ele trata a spec como algo válido para a duração de uma mudança, não necessariamente da vida inteira da feature. Ou seja: o Spec Kit te dá a ferramenta, mas não escolhe o nível por você.

2. A pergunta operacional: os três modelos de persistência do Spec Kit

A documentação oficial de Spec Persistence Models nomeia três convenções possíveis para quando os requisitos mudam. A guia Evolving Specs é o melhor complemento porque ela mostra o fluxo operacional real de cada modelo no dia a dia:

Flow-forward: cada mudança vira uma nova feature

Use este modelo quando cada pasta de feature deve permanecer como um registro histórico. O guia oficial diz que, quando surge outra feature ou uma mudança substancial, o certo é criar uma nova pasta em specs/ e continuar pela sequência padrão:

  1. rodar /speckit-specify para criar a nova feature;
  2. rodar /speckit-plan para definir a abordagem de implementação;
  3. rodar /speckit-tasks para dividir o trabalho;
  4. rodar /speckit-implement e revisar o diff de código e artefatos;
  5. rodar /speckit-converge para validar a conclusão e gerar tarefas pendentes.

O ponto importante é este: a feature antiga continua intacta. Ela vira referência histórica, comparação ou explicação de como o projeto chegou ao estado atual. Em termos práticos, a vantagem é que você nunca se pergunta “qual versão da spec é a correta?” Depois, a desvantagem é que o projeto pode começar a acumular contextos e decisões repetidas e espalhadas.

Living spec: a spec é o contrato, os outros artefatos são derivativos

Use este modelo quando spec.md deve ser a fonte de verdade da mudança. O guia instrui a seguir este fluxo:

  1. trabalhar em uma árvore limpa ou em uma branch dedicada para que cada mudança seja revisável;
  2. atualizar spec.md primeiro, seja com /speckit-clarify ou por edição manual;
  3. rodar /speckit-plan (ou editar plan.md) para que a abordagem técnica reflita a nova spec;
  4. rodar /speckit-tasks (ou editar tasks.md) para refletir o novo plano;
  5. rodar /speckit-analyze antes de retomar a implementação;
  6. rodar /speckit-implement e revisar diff do código e dos artefatos;
  7. rodar /speckit-converge para confirmar lacunas e anexar tarefas.

A chave aqui é que o contrato muda antes de tudo o resto. Isso funciona bem para features que continuam ativas e precisam evoluir sem explorar o histórico em paralelo. O risco é quem vai manter o “racional da implementação”: se o time regenerar plan/tasks e descartar decisões valiosas sem preservá-las em outro lugar, a semântica da mudança pode ficar menos clara.

Flow-back: a descoberta pode começar em qualquer artefato

Use este modelo quando a implementação ou uma revisão do trabalho revela um problema e o time aceita que a correção comece onde o insight de fato apareceu. A recomendação do guia é:

  1. capturar a descoberta no artefato mais próximo do trabalho: tasks.md, plan.md, spec.md ou até mesmo o código;
  2. decidir se a descoberta muda o comportamento pretendido, a estratégia técnica, a decomposição de tarefas ou apenas o código;
  3. atualizar os demais artefatos que agora discordam;
  4. rodar /speckit-analyze para confirmar que spec.md, plan.md e tasks.md continuam consistentes;
  5. continuar a implementação só quando o conjunto de artefatos descreve a direção que a equipe quer que futuros colaboradores sigam.

Esse é o modelo mais flexível, mas exige disciplina: se o time muda o código ou o plano sem devolver a decisão para spec.md, a base de decisão fica inconsistente. Em outras palavras, ele é ótimo para times pequenos e em troca de feedback rápido, ruim quando a equipe precisa de uma trilha clara de mudanças e decisões históricas.

ModeloRegraVantagemRisco
Flow-backEdite qualquer artefato (ou o código) primeiro, depois reconcilie tudo.Rápido; aproveita descobertas do próprio trabalho de implementação.Divergência silenciosa se ninguém reconciliar.
Flow-forwardArtefatos concluídos são imutáveis; requisito novo = pasta de feature nova.Trilha de auditoria; histórico claro.Duplicação e contexto fragmentado entre pastas.
Living specspec.md é o contrato; plan.md/tasks.md são regenerados a partir dela.Consistência forte; uma fonte única de verdade.Racional de implementação pode se perder ao regenerar.

3. Como as duas perguntas se conectam

O modelo de persistência que você escolhe determina, na prática, qual nível de SDD sua equipe realmente vive — independentemente do que a documentação promete:

  • Flow-back sem disciplina de reconciliar vira spec-first disfarçado: o arquivo continua no disco, mas ninguém mais confia nele.
  • Flow-back com reconciliação séria (rodando /speckit-analyze depois de cada descoberta) é uma forma real de spec-anchored.
  • Flow-forward é spec-anchored por feature: cada pasta individual é um bom âncora histórico, mas decisões de uma mesma capacidade se espalham por várias pastas ao longo do tempo.
  • Living spec é a versão mais completa de spec-anchored, e chega perto de spec-as-source para plan/tasks — mas o código ainda é escrito e revisado por humanos, então não é spec-as-source de verdade (isso é o que ferramentas como o Tessl tentam fazer).
As duas perguntas para decidir o modelo do seu time

1. Pastas de feature concluídas devem ser registros históricos ou áreas de trabalho editáveis?

2. spec.md é a única fonte de verdade, ou plan.md/tasks.md podem virar fontes co-iguais?

O modelo é uma convenção de time, não uma flag de CLI. Depois de decidir, documente a escolha em .specify/memory/constitution.md.

4. Pratique: escolha o modelo certo para o cenário

Cenário A: um time de 2 pessoas, mudando rápido, onde a maior parte do aprendizado acontece durante a implementação e todo mundo conversa o dia inteiro.

Flow-back. Time pequeno consegue notar e reconciliar divergência rapidamente; o custo de reconciliar é menor que o custo de burocratizar cada descoberta.

Cenário B: um produto regulado, onde auditores precisam ver exatamente quais requisitos existiam quando cada mudança foi aprovada.

Flow-forward. Cada pasta de feature vira prova histórica imutável; a duplicação é um custo aceitável frente à necessidade de auditoria.

Cenário C: uma feature central do produto, revisitada com frequência, onde o time quer que qualquer pessoa nova leia um único spec.md e confie que ele reflete o comportamento atual.

Living spec. A spec é o contrato; plan e tasks são recriados a cada mudança para continuarem consistentes com ela.

5. Uma visão crítica que vale guardar

O mesmo artigo de Böckeler questiona se times realmente conseguem seguir qualquer um desses modelos com disciplina: ela observa que, na prática, agentes de IA frequentemente ignoram partes da spec ou seguem instruções longe demais, e que revisar markdown extenso pode ser mais cansativo do que revisar código. Isso não invalida os modelos — reforça que a escolha do modelo é só metade do trabalho; a outra metade é a disciplina de reconciliar e revisar.
