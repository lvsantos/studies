Self-test: reconheça se a pilha está usando o preset

Vitória de hoje: entender os marcadores visíveis do preset de teste e usá-los para diagnosticar resolução de templates, substituição de comando e composição com wrap.

Não é uma configuração de produção

self-test é uma fixture de teste mantida dentro do repositório do Spec Kit. Seus arquivos têm marcadores explícitos como (Self-Test Preset) e preset:self-test para mostrar de onde veio um resultado. O objetivo é provar que a pilha selecionou e compôs os arquivos esperados, não orientar um fluxo de produto.

A listagem first-party do catálogo oficial inclui presets como lean e constitution-sync, mas não lista self-test como preset distribuído pelo catálogo. Para experimentá-lo, use o checkout do repositório e instale a pasta local com --dev.

1. O que a fixture fornece

O manifest substitui cinco templates do núcleo: spec-template, plan-template, tasks-template, checklist-template e constitution-template. Eles têm conteúdo pequeno e identificável, por exemplo uma spec com seções Overview, Requirements, Design e Acceptance Criteria.

Também inclui dois comandos:

  • speckit.specify substitui o comando de especificação e pede que a saída siga o template de teste, incluindo seu marcador.
  • speckit.wrap-test usa strategy: wrap. O arquivo imprime Preset Pre-Logic, insere o comando inferior em {CORE_TEMPLATE} e imprime Preset Post-Logic.

Essa segunda peça é especialmente útil: se o conteúdo central continua entre os dois marcadores, o teste demonstra que o wrapper preservou o comando inferior e acrescentou lógica antes e depois.

2. Como executar a verificação

O projeto em que você testa precisa estar inicializado com specify init. Use uma cópia de trabalho ou branch descartável: durante a instalação, os cinco templates de exemplo ganham precedência sobre os equivalentes inferiores.

# A partir de um clone local do repositorio github/spec-kit
specify preset add --dev ./presets/self-test
specify preset list
specify preset resolve spec-template
specify preset resolve speckit.specify
specify preset resolve speckit.wrap-test

Depois, gere uma spec com o comando registrado na integração ativa e procure o cabeçalho e o comentário preset:self-test. Inspecione também o conteúdo efetivo de speckit.wrap-test: a lógica central deve estar presente entre as seções Pre-Logic e Post-Logic.

  1. Se resolve aponta para o arquivo do preset, a camada venceu para aquele nome.
  2. Se o artefato gerado tem o marcador, o agente usou o comando/template pretendido.
  3. Se o wrapper perdeu conteúdo central, verifique a estratégia declarada e o placeholder {CORE_TEMPLATE}.
  4. Remova a fixture ao terminar para restaurar os arquivos e comandos do fluxo normal.
specify preset remove self-test

3. O que ele não prova

Um marcador confirma origem e composição, não qualidade de requisitos, compatibilidade semântica ou segurança. Os templates deliberadamente simples não são um ponto de partida adequado para especificações reais. O comando de teste também não valida sozinho todas as integrações de agentes: confira o comando materializado na integração ativa e execute o fluxo que deseja testar.

Use self-test para depurar a infraestrutura de presets, ou como exemplo ao desenvolver um preset. Para reduzir boilerplate no uso cotidiano, avalie lean; para criar uma regra própria, use o scaffold.

4. Pratique: onde está a falha?

specify preset resolve speckit.wrap-test mostra o arquivo do preset, mas ao executar o comando só aparece o texto central, sem os marcadores antes e depois. Qual é a primeira coisa a inspecionar?

Confira manifest e placeholder de composição. O item deve usar a estratégia wrap e o arquivo precisa conter {CORE_TEMPLATE}; depois confira o comando que foi registrado na integração ativa.
