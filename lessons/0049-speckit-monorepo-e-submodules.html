Escolha o contexto Spec Kit pelo projeto, não pelo Git

Vitória de hoje: manter um único ciclo Spec Kit no repositório pai quando uma feature atravessa submodules e respeitar as regras de cada repo.

A unidade de Spec Kit é a pasta com .specify/

Um monorepo pode conter vários projetos Spec Kit independentes, cada qual com sua constituição e pasta specs/. Executar os comandos de dentro de um projeto seleciona o .specify/ mais próximo. O layout do Git não define as fronteiras de interface: se componentes colaboram, o contrato continua sendo acordado e testado. Guia oficial de monorepo.

Monorepo: contexto local, Git compartilhado

repo/
  apps/web/.specify/       # specs e constituição do web
  apps/api/.specify/       # specs e constituição da API
  packages/ui/.specify/    # specs e constituição do pacote

Rode o fluxo no diretório do projeto responsável. Em execução não interativa, SPECIFY_INIT_DIR=apps/api seleciona o projeto a partir da raiz, desde que o caminho exista e contenha .specify/. A variável precisa chegar ao shell que executa os scripts do agente; valide que os artefatos foram escritos na pasta esperada.

Com um único repositório Git na raiz, branches e commits continuam compartilhados por todo o monorepo. As specs são locais ao projeto selecionado; Git não cria uma branch isolada por subpasta. Veja o detalhe de Git no guia.

Uma feature, um único ciclo

  1. specify: descreva a feature no projeto pai e liste os repos/submodules que serão alterados.
  2. plan: produza um plano único que atravesse as fronteiras, com contratos, caminhos e ownership claros.
  3. tasks: mantenha uma lista única; marque cada tarefa com o repo-alvo, suas regras locais e os checks que deve cumprir.
  4. implement: execute a mesma lista no workspace com submodules inicializados e valide os checks de cada repo e a integração final.

Esse modelo funciona quando os repos compõem uma única mudança coordenada. Git ainda mantém commits e branches separados dentro de cada submodule; uma execução de implement não torna esses históricos um único commit. A lição anterior detalha como acordar contratos entre os componentes.

Constitutions: coordenação no pai, regras nos repos

Inicialize o Spec Kit somente no repositório pai. Ele tem a spec e a constitution usadas pelo único ciclo; não inicialize outro projeto Spec Kit nos submodules para essa feature. O Spec Kit não descobre nem herda automaticamente constitutions por submodule: a constitution do pai não substitui as regras de cada repo.

produto-repo/                 # projeto integrador, se fizer sentido
  .specify/memory/constitution.md  # regras globais e instrução de coordenação
  specs/023-feature/
    spec.md
    plan.md
    tasks.md
  modules/api/                 # submodule; outro repositório
    CONSTITUTION.md              # regras locais, mantidas neste repo
  modules/web/                 # outro submodule
    CONSTITUTION.md
  1. Deixe a constitution do pai com princípios transversais e uma regra explícita: antes de alterar um submodule, leia seu CONSTITUTION.md e siga seus checks.
  2. Mantenha cada CONSTITUTION.md no repo que governa, com revisão dos responsáveis por aquele repo. Não copie seu conteúdo para o pai como segunda fonte de verdade.
  3. Na spec.md/plan.md, liste os repos afetados e os caminhos das constitutions. Em tasks.md, associe cada tarefa e validação ao repo correspondente.
  4. O agente precisa receber esses arquivos no contexto. A constitution do pai não os carrega automaticamente; inclua a instrução no contexto compartilhado e confirme durante o plano que foram lidos.

Como o pai fixa um commit de cada submodule, a revisão escolhida também fixa a versão da constitution local vista pelo workspace. Mudanças nessas regras são commits no repo dono; depois atualize o gitlink do pai se a feature depender da nova revisão. Uma spec/plan/tasks cobre a mudança coordenada; os commits Git continuam separados por repo. Para checkout completo, use git clone --recurse-submodules. Pratique: como carregar as regras locais?

Uma feature no repo pai altera dois submodules, cada qual com seu próprio padrão de testes. Você quer um único ciclo Spec Kit. Como manter as regras locais sem criar projetos Spec Kit nos filhos?
