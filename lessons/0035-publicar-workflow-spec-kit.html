Publicar seu workflow: release e catálogo comunitário

Vitória de hoje: deixar um workflow instalável a partir do seu repositório e decidir se também vale submetê-lo para descoberta no catálogo comunitário.

Pacote e descoberta são etapas diferentes

Seu repositório hospeda o workflow e suas releases. O catálogo comunitário do Spec Kit aponta para uma URL versionada para que as pessoas encontrem o pacote em specify workflow search. Publicar no GitHub não o coloca automaticamente no catálogo; entrar no catálogo também não transforma o workflow em código auditado ou endossado.

Esse modelo é parecido com os exemplos de publicação de extensão e publicação de preset, mas cada tipo tem seu próprio arquivo, catálogo e comando.

1. Organize o repositório próprio

Partindo do workflow feature-review da lição anterior, mantenha o pacote pequeno e compreensível:

spec-kit-workflow-feature-review/
├── workflow.yml
├── README.md
├── LICENSE
└── CHANGELOG.md

O guia oficial pede YAML válido, README com descrição, entradas e grafo de etapas, licença, versão SemVer e teste em projetos reais. O changelog é recomendado. Explique dependências, quais integrações foram testadas e qualquer uso de shell, arquivos ou credenciais.

2. Teste antes de criar a release

Use a pasta local em um projeto de laboratório. Inspecione a definição e execute o fluxo completo, incluindo pelo menos uma aprovação e uma rejeição de gate:

specify workflow info ./workflow.yml
specify workflow run ./workflow.yml \
  --input spec="Adicionar exportação CSV ao histórico de ordens" \
  --input integration=copilot

Confirme que a pausa, a retomada e as saídas correspondem ao README. info valida a definição e exibe metadados; não executa os steps nem analisa o conteúdo de shell.run.

3. Publique uma versão no seu repositório

Atualize workflow.version e o CHANGELOG.md, faça commit e crie uma tag correspondente. Por exemplo:

git add workflow.yml README.md LICENSE CHANGELOG.md
git commit -m "Release feature-review 1.0.0"
git tag v1.0.0
git push origin main --tags

O endereço raw do YAML deve apontar para a tag, não para main, para que a versão não mude silenciosamente:

https://raw.githubusercontent.com/acme/spec-kit-workflow-feature-review/v1.0.0/workflow.yml

Teste esse mesmo endereço em um projeto Spec Kit limpo. A instalação direta não depende de inclusão em catálogo:

specify workflow add feature-review --from \
  https://raw.githubusercontent.com/acme/spec-kit-workflow-feature-review/v1.0.0/workflow.yml
specify workflow list
specify workflow remove feature-review

4. Se quiser aparecer na busca comunitária

A listagem comunitária é para descoberta e, por padrão, não permite instalar por ID. O pacote continua hospedado no seu repositório; você contribui com os metadados que apontam para a release:

  1. Faça fork de github/spec-kit e crie uma branch.
  2. Edite workflows/catalog.community.json; insira seu item em workflows na ordem alfabética do ID.
  3. Inclua URL raw com tag, repositório, licença, requisito mínimo, tags e datas coerentes com a release.
  4. Abra um pull request para github/spec-kit com o YAML validado, README, licença e evidência de teste.
  5. Responda às verificações dos mantenedores; não presuma que a entrada já está disponível antes da aprovação e publicação do PR.

O formato do catálogo é JSON. Um item reduzido se parece com isto:

{
  "feature-review": {
    "id": "feature-review",
    "name": "Feature Review",
    "description": "Gera uma spec, pede revisão e cria o plano",
    "author": "Acme Engineering",
    "version": "1.0.0",
    "url": "https://raw.githubusercontent.com/acme/spec-kit-workflow-feature-review/v1.0.0/workflow.yml",
    "repository": "https://github.com/acme/spec-kit-workflow-feature-review",
    "license": "MIT",
    "requires": { "speckit_version": ">=0.8.5" },
    "tags": ["sdd", "review"],
    "created_at": "2026-10-03T00:00:00Z",
    "updated_at": "2026-10-03T00:00:00Z"
  }
}

O exemplo usa dados ilustrativos: troque autor, URL, requisitos e datas pelos dados reais. Ao lançar outra versão, publique nova tag e abra outro PR atualizando version e url do catálogo.

5. Entenda o que a revisão comunitária significa

O processo verifica principalmente formato e completude: definição válida, etapas coerentes, entradas compreensíveis e documentação. Isso não é auditoria sistemática de segurança. Um step shell executa com os privilégios do usuário; leia o YAML publicado e revise cada campo run antes de instalar, mesmo que esteja listado no catálogo.

Se sua equipe controla uma lista instalável própria, o catálogo organizacional é outra opção de distribuição. Não confunda essa política com o catálogo comunitário padrão, que serve para descobrir workflows e não autoriza instalação por ID.

6. Pratique: release ou catálogo?

Uma colega instala seu workflow pela URL raw versionada, mas ele não aparece na busca comunitária. Qual ação falta?
