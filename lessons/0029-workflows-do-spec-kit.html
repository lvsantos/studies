Workflows: transformar etapas em um processo repetível

Vitória de hoje: decidir quando um workflow resolve o problema, acompanhar uma execução e distingui-lo de uma extension ou preset.

O problema que resolve

Um processo com várias etapas depende da pessoa lembrar a ordem, passar os dados certos, fazer as revisões no momento adequado e retomar o trabalho se algo parar no meio. Isso funciona até que a sequência varie entre sessões, pessoas ou projetos.

Um workflow coloca essa sequência em uma definição YAML executável. O Spec Kit coordena os passos, registra o estado e permite retomar uma execução pausada ou falha. Ele não substitui o julgamento sobre o resultado: os checkpoints humanos continuam fazendo parte do processo.

1. Uma definição, várias etapas

Um workflow tem metadados e requisitos, entradas declaradas e uma lista ordenada de passos. As entradas podem ser obrigatórias, tipadas, ter padrão e opções permitidas. Cada passo recebe um identificador e pode usar valores recebidos ou saídas de passos anteriores.

inputs:
  spec:
    type: string
    required: true
    prompt: "O que você quer construir?"

steps:
  - id: specify
    command: speckit.specify
    input:
      args: "{{ inputs.spec }}"
  - id: review-spec
    type: gate
    message: "Revise a spec antes de continuar."
    options: [approve, reject]
    on_reject: abort
  - id: plan
    command: speckit.plan

Este fragmento mostra a ideia central: executar um comando, parar num gate para revisão e só então seguir. Na definição oficial completa, o workflow speckit encadeia specify, revisão da spec, plan, revisão do plano, tasks e implement.

2. O motor de execução

Os passos não se limitam a chamar comandos de feature. Um workflow também pode enviar um prompt ao agente, executar um comando de shell, inicializar um projeto, aguardar aprovação, ramificar por condição ou repetir um trecho. Há ainda fan-out/fan-in para distribuir uma etapa sobre itens e reunir os resultados.

  1. Entrada: quem inicia fornece os valores exigidos ou responde às perguntas interativas.
  2. Execução: o motor percorre os passos na ordem definida e resolve expressões como {{ inputs.spec }}.
  3. Controle: gates podem pausar para uma decisão humana; condições e loops adaptam a rota.
  4. Estado: progresso e resultados ficam registrados em .specify/workflows/runs/<run_id>/.
  5. Retomada: consulte o status e continue uma execução pausada ou falha a partir do ponto registrado.

Estados comuns são running, completed, paused, failed e aborted. Uma falha normalmente interrompe a execução; ao retomar, o passo que falhou é tentado novamente. Um gate não aprova nada sozinho: a pessoa revisa e chama resume.

3. Por que usar um workflow?

BenefícioO que muda no trabalho
RepetibilidadeA mesma sequência e os mesmos checkpoints são aplicados sempre que o processo é iniciado.
Menos carga de memóriaA pessoa não precisa lembrar a próxima etapa nem reconstruir manualmente quais dados passar.
Revisão no momento certoGates podem exigir revisão da spec ou do plano antes de trabalho posterior.
Retomada rastreávelO estado da execução deixa visível onde parou; não é preciso tratar cada pausa como um recomeço.
AdaptaçãoCondições e loops permitem caminhos diferentes, recuperação explícita ou repetição controlada.

O ganho não é “automatizar tudo”. É tornar explícito o que deve acontecer e em que ordem, deixando decisões importantes com uma pessoa e tarefas mecânicas com o motor.

4. Workflow, extension ou preset?

BlocoPergunta que respondeExemplo
WorkflowEm que ordem, com quais desvios e aprovações as etapas acontecem?Executar specify → review → plan → review → tasks → implement.
ExtensionQue comando, integração ou capacidade ainda não existe?Adicionar comandos de bug fixing ou conectar uma ação ao Jira.
PresetComo um processo ou artefato existente deve ser instruído ou formatado?Exigir uma seção de segurança no plano e orientar o agente a preenchê-la.

Uma extensão oferece passos que podem ser usados; um workflow organiza esses passos numa sequência. Os workflows oficiais bugfix e assess, por exemplo, chamam comandos fornecidos pelas extensões correspondentes. Já um preset altera templates ou comandos existentes: ele não é o mecanismo que controla a ordem, a pausa ou a retomada.

Os blocos podem trabalhar juntos. Um workflow pode chamar comandos de uma extensão e usar comandos ou templates influenciados por presets. Para adaptar a sequência existente sem editar a cópia instalada, workflows também têm overlays; eles editam passos por âncoras e são diferentes dos overlays de template/resolução de presets.

5. Experimentar no projeto

A maioria dos comandos de workflow pressupõe um projeto preparado com specify init. Primeiro descubra e inspecione; depois instale e execute:

specify workflow search
specify workflow info speckit
specify workflow add speckit
specify workflow list
specify workflow run speckit --input spec="Build a kanban board"
specify workflow status
specify workflow resume <run_id>

Também é possível executar um YAML local com specify workflow run ./workflow.yml --input chave=valor. A exceção é útil para experimentar sem instalar um workflow; passos que dependem de comandos ou integrações ainda precisam encontrá-los no ambiente.

Um gate pausa; resume continua a mesma execução

No workflow speckit, a primeira execução chama specify para gerar a spec e então chega ao gate review-spec. Nesse ponto, a execução fica pausada e o comando informa um run_id. Revise o arquivo gerado e consulte o status se precisar localizar essa execução:

specify workflow status
specify workflow status <run_id>
specify workflow resume <run_id>

Se você aprovar: o gate libera a continuação da mesma execução. O workflow roda plan e para novamente em review-plan. Depois de revisar o plano, retome com o mesmo run_id; então ele segue por tasks e implement, até concluir.

Se você rejeitar: no workflow oficial, on_reject: abort encerra essa execução; não apaga os arquivos que ela já gerou. A spec fica na pasta da feature em specs/. Neste projeto, uma nova chamada a specify escolhe o próximo número livre e cria outra pasta; repetir o workflow com a mesma ideia pode, portanto, deixar duas features semelhantes, sem substituir a primeira.

Para corrigir sem duplicar: enquanto a execução ainda estiver pausada em review-spec, edite o spec.md gerado, revise a versão corrigida e aprove o gate; o workflow seguirá no mesmo run_id. Se você já rejeitou e o run foi abortado, a spec continua no disco. Confira .specify/feature.json para confirmar que essa pasta continua sendo a feature ativa e prossiga a partir dela com /speckit.plan na integração, ou use uma workflow que comece em plan. Não inicie outro speckit completo a menos que queira criar uma feature nova.

Em qualquer pausa, use workflow resume <run_id> para continuar, não workflow run. Aprovar é uma decisão humana para continuar, não uma validação automática da qualidade do documento.

Segurança e limites

Um passo shell executa um comando local com os privilégios do usuário; o engine não oferece sandbox. Valores interpolados em run são inseridos sem escape automático. Revise o YAML antes de executar, evite passar conteúdo não confiável para shell e restrinja entradas com uma lista permitida quando isso fizer sentido. Workflows comunitários são mantidos por seus autores e não são auditados ou endossados pelo Spec Kit.

6. Pratique: escolha o bloco

Cenário A: toda feature deve seguir uma sequência com revisão humana entre spec e plan, e entre plan e tasks. Qual bloco organiza essa sequência?

Cenário B: a equipe precisa de um comando novo que avalia um bug e outro que guia sua correção. Qual bloco fornece essas capacidades?

Cenário C: todo plano deve ter uma seção de segurança e instruções para o agente registrá-la. Qual bloco adapta o processo existente?
