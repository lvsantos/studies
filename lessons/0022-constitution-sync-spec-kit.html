Constitution-sync: quando a regra precisa aparecer nos arquivos

Vitória de hoje: distinguir a constituição lida em tempo de execução de cópias materializadas para revisão e aprender a ativar essa propagação deliberadamente.

O problema que resolve

O Spec Kit padrão mantém a constituição viva como fonte de verdade: comandos como plan, tasks e analyze leem o arquivo atual. Isso evita cópias desatualizadas, mas pode não bastar quando a equipe quer revisar em PR, como artefatos versionados, as regras concretas que orientarão templates e comandos.

constitution-sync é uma opção explícita para materializar essas regras em scaffolds e orientações locais. Não substitui o modelo padrão; acrescenta cópias revisáveis e assume o trabalho de mantê-las coerentes.

1. O que o preset realmente fornece

O manifest requer Spec Kit >= 0.14.4 e fornece um único comando: speckit.constitution, com estratégia wrap. O preset envolve o comando atual via {CORE_TEMPLATE}, preservando o fluxo central e adicionando uma etapa de propagação depois que a constituição é escrita.

Há dois momentos diferentes:

  • Ao instalar ou reconciliar a pilha: o preset pode materializar o constitution-template resolvido em .specify/memory/constitution.md. Em mudanças posteriores na pilha, só substitui o arquivo vivo se o hash ainda corresponder ao conteúdo gerado; uma edição humana impede a substituição automática.
  • Ao executar o comando de constituição: ele alinha os templates locais de plano, spec e tarefas, orientações do projeto e comandos locais não geridos por outros presets/extensões. Depois registra no Sync Impact Report quais arquivos foram atualizados.

Mesmo com esse preset, comandos de runtime continuam lendo a constituição viva. A cópia materializada é uma camada adicional, não uma nova fonte de verdade.

2. Exemplo: uma regra nova precisa chegar ao fluxo

Imagine um projeto cuja constituição diz: “Toda mudança em uma API deve ter testes de contrato.” Sem constitution-sync, o plan ainda pode consultar a constituição viva durante a execução, mas os templates versionados do projeto podem continuar mostrando apenas o lembrete genérico:

## Constitution Check

[Gates determined based on constitution file]

Com o preset instalado, a pessoa atualiza os princípios usando /speckit.constitution. O comando central continua fazendo seu trabalho normal; em seguida, o wrapper faz uma passada de consistência nos artefatos locais. Por exemplo, o plan-template.md pode passar a incluir um gate concreto como:

## Constitution Check

- [ ] Mudanças de API incluem testes de contrato.

O mesmo passe pode ajustar o spec-template.md para pedir critérios de aceitação compatíveis, o tasks-template.md para lembrar a tarefa de teste e documentos/comandos locais para remover instruções antigas. O Sync Impact Report da constituição registra quais caminhos foram atualizados. As frases acima são um exemplo do resultado esperado, não texto fixo que o preset sempre insere: o conteúdo depende dos princípios reais e da revisão feita pelo agente.

Resultado prático: quem revisa um PR pode ler o gate no próprio template versionado, antes de gerar um plano. Sem esse preset, a equipe pode manter o ponteiro genérico e deixar o comando consultar a constituição viva quando for usado.

3. Como usar com segurança

O projeto precisa estar inicializado com specify init. Confira a versão do Spec Kit e use o preset somente se a equipe quer que os arquivos materializados sejam revisados e commitados.

specify preset add constitution-sync
specify preset list
specify preset resolve speckit.constitution

Depois, na integração de agente ativa, execute /speckit.constitution (ou o nome equivalente que a integração registrou) e revise o diff inteiro. Ao mudar princípios, execute o comando de novo; não presuma que uma edição da constituição propagou sozinha para todos os arquivos derivados.

  1. Revise a constituição resultante e o Sync Impact Report.
  2. Revise mudanças em .specify/templates/, comandos locais e documentos de orientação.
  3. Confirme com specify preset resolve quais arquivos são controlados por presets ou extensões.
  4. Faça commit só depois de confirmar que cópias geradas e a constituição dizem a mesma coisa.

Há ainda um efeito de orientação: substituir no plan-template.md o ponteiro dinâmico de Constitution Check por gates concretos pode fazer o primeiro /plan se ancorar em texto congelado. Mantenha o ponteiro, a menos que a equipe queira deliberadamente versionar aqueles gates ali.

5. Quando escolher e quando não

Escolha-o se revisores precisam ler e aprovar os gates materializados junto com templates e comandos locais. Evite-o se o modelo de resolução em tempo de execução já atende à equipe, ou se boa parte do fluxo é gerida por outros presets e extensões. Nesse cenário, o stack composável mantém uma única constituição viva sem cópias que possam derivar.

Para voltar ao comportamento padrão, redefina as seções materializadas de Constitution Check para o ponteiro dinâmico indicado no README oficial e remova o preset:

specify preset remove constitution-sync

A remoção não decide como reconciliar texto local já materializado; revise o diff e restaure conscientemente os ponteiros antes ou depois de remover.

6. Pratique: uma equipe mudou de modelo

A equipe quer que o PR mostre os gates exatos, mas seu template de plano é fornecido por outra extensão. O que deve investigar antes de instalar constitution-sync?

Verifique a propriedade do template e resolva sua origem. O preset não deve editar arquivos versionados de outra extensão; a reconciliação pode sobrescrevê-los. Nesse fluxo, prefira a resolução dinâmica ou crie uma camada organizacional compatível e governada.
