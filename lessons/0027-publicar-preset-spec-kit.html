Publicar um preset: do seu repositório ao catálogo comunitário

Vitória de hoje: conseguir empacotar um preset para instalação reproduzível e distinguir publicar no seu GitHub de submetê-lo para descoberta no Spec Kit.

A diferença que organiza o fluxo

O repositório próprio é a origem do pacote: guarda manifest, templates, comandos, documentação e releases. O catálogo comunitário do Spec Kit é uma vitrine de descoberta: aponta para essa origem e permite que as pessoas encontrem o preset com specify preset search.

São etapas separadas. Um preset pode estar publicado e instalável pelo seu URL de release sem aparecer no catálogo. E aparecer no catálogo não significa que os mantenedores auditaram ou endossaram seu conteúdo.

1. Use o preset da lição anterior como pacote

Na lição 26, criamos security-review, que acrescenta uma revisão de segurança ao template de plano. Vamos supor que os testes passaram e que o pacote será mantido em https://github.com/acme/spec-kit-security-review. O nome é ilustrativo; substitua organização, URL, ID e versão pelos seus.

Uma estrutura simples de repositório fica assim:

spec-kit-security-review/
├── preset.yml
├── README.md
├── LICENSE
├── CHANGELOG.md          # recomendado
└── templates/
    └── plan-security-addendum.md

Em um monorepo, os arquivos podem morar numa subpasta, como presets/security-review/. O importante é que preset.yml e os caminhos declarados nele estejam dentro da raiz do pacote que será instalado, e que a URL documentation leve ao README específico desse preset.

2. Prepare o repositório próprio

Antes de publicar, trate o preset como um produto pequeno, não como uma pasta que por acaso funciona na sua máquina:

  1. Manifesto: mantenha preset.yml válido; use ID único em minúsculas e hífens, versão SemVer como 1.0.0, descrição concisa, URL pública do repositório, licença e requisito mínimo do Spec Kit.
  2. Arquivos fornecidos: confira cada caminho em provides.templates e provides.commands; remova exemplos do scaffold que não pertencem ao produto.
  3. Dependências: se um comando substituído depende de uma extensão, declare-a em requires.extensions. Sem essa declaração, o preset ainda pode instalar e a instrução que depende dela simplesmente não produzir o efeito esperado.
  4. README: explique o que o preset fornece, quando usar e quando não usar, requisitos, limitações e como instalar. O README deve documentar este preset, não apenas apresentar um framework maior.
  5. Licença e histórico: inclua LICENSE; mantenha CHANGELOG.md para registrar mudanças por versão.

Para uma submissão comunitária, o README ligado no catálogo precisa ser uma página GitHub legível cujo caminho termine em README.md e conter pelo menos um comando specify preset add .... Em monorepo, use o README dentro da pasta do preset, não o README de marketing na raiz.

3. Teste a pasta e o artefato real

Use um projeto de laboratório já inicializado com specify init. O modo --dev instala a pasta local e testa o desenvolvimento; não publica nada:

specify preset add --dev ../spec-kit-security-review
specify preset info security-review
specify preset list
specify preset resolve plan-template
specify preset remove security-review

Não pare em resolve. Gere ou atualize um plano com o agente e verifique se a seção de segurança realmente aparece, se o restante do plano foi preservado e se comandos substituídos (se houver) foram materializados no diretório do agente ativo. Repita em outro agente quando você declarar compatibilidade com ele. Remova o preset ao final para não contaminar o projeto de teste.

A checagem que pode reprovar a hipótese de “está pronto” é direta: se a versão instalada do ZIP não produz o comportamento observado com --dev, ainda não publique; primeiro descubra se o problema está no manifest, nos caminhos, no empacotamento ou no README.

4. Crie uma versão instalável no seu GitHub

O valor em preset.yml é 1.0.0; a tag normalmente é v1.0.0. Atualize manifesto e changelog antes de marcar a release:

git add preset.yml CHANGELOG.md README.md LICENSE templates/
git commit -m "Release security-review 1.0.0"
git tag v1.0.0
git push origin main --tags

Com a tag no GitHub, o arquivo-fonte compactado fica disponível neste formato:

https://github.com/acme/spec-kit-security-review/archive/refs/tags/v1.0.0.zip

Faça o último teste usando essa URL exata, não apenas a pasta local:

specify preset add --from \
  https://github.com/acme/spec-kit-security-review/archive/refs/tags/v1.0.0.zip
specify preset resolve plan-template
specify preset remove security-review

O teste de arquivo detecta problemas que o modo --dev pode esconder, como uma release que não contém o diretório esperado ou README que aponta para outra versão. Use esse mesmo comando no README, assim quem lê já consegue instalar a versão publicada.

5. Se quiser, publique somente no seu repositório

Essa etapa já permite compartilhar: mantenha o repositório público, publique releases com tags e dê aos usuários a URL de instalação --from. Não é necessário alterar o Spec Kit nem esperar inclusão em catálogo. É uma boa opção para:

  • um preset da equipe cuja descoberta será feita pela documentação interna;
  • uma primeira versão pública que você ainda quer observar com usuários;
  • uma distribuição controlada por link direto.

Se várias equipes vão instalar pelo catálogo interno de uma organização, o repositório do preset continua sendo a origem; o catálogo organizacional é outra camada de distribuição. A lição 19 sobre extensões explica a diferença entre URL direta e catálogo. Para presets, siga os comandos e o modelo de catálogo próprios descritos no guia de publicação.

6. Submeta para descoberta no catálogo da comunidade

Para aparecer na busca comunitária, contribua para o repositório github/spec-kit. O guia oficial descreve uma mudança de catálogo por pull request, não a publicação do pacote dentro do repositório do Spec Kit:

  1. Faça fork e clone de github/spec-kit; crie uma branch para a submissão.
  2. Edite presets/catalog.community.json: insira a entrada dentro de presets, ordenada alfabeticamente pelo ID do preset.
  3. Edite docs/community/presets.md: acrescente uma linha à tabela comunitária, ordenada alfabeticamente pelo nome exibido.
  4. Abra um PR com as duas mudanças e preencha a descrição/checklist pedida pelo guia e pelo repositório.
  5. Acompanhe validação e revisão: corrija metadados, README, compatibilidade e problemas encontrados. A entrada só passa a ser apresentada como verificada depois da validação e aprovação previstas pelo projeto.

Uma entrada reduzida tem esta forma. Conte os arquivos fornecidos a partir do pacote real e mantenha as datas/URLs coerentes com a release:

{
  "security-review": {
    "name": "Security Review",
    "id": "security-review",
    "version": "1.0.0",
    "description": "Adds a security review to feature plans",
    "author": "Acme Engineering",
    "repository": "https://github.com/acme/spec-kit-security-review",
    "download_url": "https://github.com/acme/spec-kit-security-review/archive/refs/tags/v1.0.0.zip",
    "documentation": "https://github.com/acme/spec-kit-security-review/blob/v1.0.0/README.md",
    "license": "MIT",
    "requires": { "speckit_version": ">=0.1.0" },
    "provides": { "templates": 1, "commands": 0 },
    "tags": ["security", "planning"]
  }
}

O hash SHA-256 é opcional no formato descrito pelo guia, mas pode ser incluído quando calculado para exatamente o arquivo indicado em download_url. Não copie contagens, versão, link de README ou hash de outro preset. Os links de documentação devem ser acessíveis antes do download.

7. O que a revisão comunitária verifica

Espere análise do manifesto e dos arquivos, qualidade dos templates, coerência entre comandos e seções, segurança de conteúdo/operações e documentação. A validação automatizada consegue conferir itens objetivos, incluindo README alcançável e existência de comando de instalação; pessoas ainda avaliam se o material realmente descreve aquele preset e se faz sentido para usuários.

O guia menciona que uma automação é acionada após a triagem aplicar o rótulo preset-submission a um issue. Se a contribuição ficar aguardando essa triagem, isso não significa que você possa aplicar o rótulo ou que precise insistir nele: siga o estado e as instruções do processo atual dos mantenedores.

O catálogo comunitário é principalmente para descoberta. Não trate a presença de metadados, a listagem em specify preset search ou o rótulo de verificação como garantia de segurança para qualquer ambiente. Leia o código e a documentação antes de instalar, conforme a orientação de presets comunitários.

8. Atualize sem quebrar quem já instalou

Para cada nova versão, atualize o campo version em preset.yml e o CHANGELOG.md, crie e envie uma nova tag, teste o novo arquivo compactado e abra um PR para atualizar version e download_url no catálogo comunitário. O repositório do preset e o catálogo são duas fontes de informação: atualizar só uma deixa a descoberta apontando para uma versão antiga.

Uma alteração incompatível merece nova versão principal SemVer; correção compatível incrementa a versão de patch. Nunca reutilize uma tag já publicada para conteúdo diferente: a URL precisa identificar o artefato que foi revisado.

9. Pratique: qual é o próximo passo?

Você já publicou security-review como release no seu GitHub. Uma colega instalou com --from, mas o preset não aparece em specify preset search. O que falta para a busca comunitária conhecê-lo?

A submissão ao repositório do Spec Kit: adicionar a entrada ordenada ao presets/catalog.community.json, adicionar a linha à tabela em docs/community/presets.md e abrir o PR para revisão. O pacote continua hospedado no seu repositório. Até a inclusão, o URL da release continua sendo o caminho de instalação direta.

Fonte primária recomendada

Siga o Preset Publishing Guide para estrutura, release, README, catálogo e revisão. Compare com o catálogo comunitário atual e a página oficial de presets comunitários; metadados e validações podem mudar.
