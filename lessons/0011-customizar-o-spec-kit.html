Como customizar o Spec Kit

Vitória de hoje: escolher o ponto certo de customização sem alterar o núcleo do processo por acidente.

A ideia central

O Spec Kit já traz processos prontos, mas você pode adaptá-los ao domínio, à equipe e às ferramentas do projeto. A primeira decisão é identificar o que está mudando: capacidade, formato, processo local ou pacote de configuração.

Comece pequeno. Uma customização deve resolver uma necessidade real e ser fácil de revisar, remover ou substituir.

1. Escolha o bloco certo

NecessidadeBloco provávelIdeia
Adicionar um comando, integração ou fase novaExtensionAmplia o que o Spec Kit consegue fazer.
Mudar o formato de spec, plan ou tasksPresetAltera templates e instruções sem criar uma capacidade nova.
Ajustar um único projetoOverride localAplica uma mudança em .specify/templates/overrides/.
Automatizar vários passosWorkflowEncadeia comandos ou etapas de um processo.
Distribuir uma configuração completaBundleCombina extensões, presets e workflows para um papel ou equipe.

2. Extensions: adicionar capacidade

Uma extensão pode trazer comandos, templates, scripts, hooks ou integração com uma ferramenta externa. Exemplos possíveis: integração com Jira, revisão de código depois da implementação ou rastreabilidade de testes.

specify extension search
specify extension add <extension-name>

Use extensão quando a pergunta for: “o Spec Kit precisa fazer algo novo?” Leia o código e a documentação da extensão antes de instalá-la.

3. Presets: mudar como o processo funciona

Um preset modifica templates ou comandos existentes para impor uma convenção. Pode acrescentar rastreabilidade regulatória, uma revisão de segurança ou uma ordem específica de testes.

specify preset search
specify preset add <preset-name>

Use preset quando a pergunta for: “o processo já serve, mas precisa falar ou exigir algo diferente?” Presets podem ser combinados com prioridades, por isso a precedência importa.

4. Overrides, workflows e bundles

Override local: para uma alteração específica deste projeto. É apropriado quando ainda não existe uma convenção reutilizável. A resolução padrão procura primeiro os overrides locais, depois presets, extensões e, por fim, os templates do núcleo.

Workflow: para automatizar uma sequência de passos. Ele não é apenas um template diferente; descreve como várias ações se encadeiam.

Bundle: para entregar uma configuração curada em uma instalação. Um bundle pode fixar versões e reunir os componentes necessários para um papel, como desenvolvedor, analista ou pesquisador de segurança.

5. O que customizar primeiro

  1. Confirme se uma skill ou processo existente já resolve o problema.
  2. Se a mudança for local e experimental, use um override.
  3. Se a regra precisar ser reutilizada, avalie um preset.
  4. Se houver nova capacidade ou integração, avalie uma extensão.
  5. Se várias escolhas precisarem viajar juntas, avalie um bundle.

Não crie uma extensão para apenas trocar uma frase de um template. Não use um preset para esconder uma integração externa que deveria ser uma extensão.

6. Pratique: escolha o bloco

Uma equipe quer que todo plan.md inclua uma seção obrigatória de revisão de segurança em todos os projetos. Qual bloco parece mais adequado?

Um preset. A equipe quer mudar o formato e a exigência do processo existente. Se, além disso, fosse necessário integrar uma ferramenta externa de segurança, essa integração poderia ser uma extensão.
