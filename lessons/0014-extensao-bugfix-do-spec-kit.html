Bug fix: quando o problema já existe e precisa de diagnóstico

Vitória de hoje: saber quando usar a extensão de bug fix, como instalá-la, como executar o fluxo assess → fix → test e como distinguir uma extensão oficial do Spec Kit de uma extensão da comunidade.

O mapa mental

Essa extensão não é para criar uma feature nova; ela é para reparar o que já está quebrado.

É uma extensão oficial do Spec Kit, não da comunidade. Ela é “bundled, opt-in” — vem junto como parte do kit, mas precisa ser instalada explicitamente antes de usar.

1. O que ela resolve?

O problema que ela resolve é o clássico de “o sistema está quebrado e o time precisa de um processo objetivo para descobrir a causa, corrigir a causa e verificar a correção sem improviso.”

Em vez de ir direto para patch, ela institucionaliza três passos:

  1. Assess: diagnosticar se o relato é um bug real, localizar a área suspeita e propor uma remediação;
  2. Fix: aplicar a correção avaliada e registrar o que mudou;
  3. Test: reproduzir o problema e validar que a correção funcionou, sem afirmar mais do que a evidência suporta.

Ela funciona bem quando o trabalho não é “nova funcionalidade”, mas “reparo de comportamento quebrado”.

2. Quando usar

Use essa extensão quando a situação tiver este formato:

  • há um bug reportado, stack trace, URL de issue ou reprodução conhecida;
  • o objetivo é localizar e corrigir a causa raiz, não só esconder o sintoma;
  • há necessidade de registrar evidência do diagnóstico e da correção em arquivos do projeto;
  • o time quer separar claramente “diagnóstico”, “correção” e “verificação”.

Ela não substitui o fluxo de feature do Spec Kit. Ela é um fluxo dedicado para reparos, e a documentação oficial a apresenta como um processo separado do SDD de feature.

3. Como instalar

A instalação é simples e ocorre via CLI do Spec Kit:

specify extension add bug

Isso instala a extensão oficial do Spec Kit. Ela é opt-in, então o comando acima é o passo de ativação; depois disso, as skills do agente ficam disponíveis no ambiente do seu editor ou do session manager da integração.

Importante: o comando de terminal só instala a extensão. Os comandos reais de bug fix são executados pelo agente na conversa, e não diretamente em shell.

4. Como usar

O processo usa um único identificador para cada bug: o slug. Ele vira o diretório de artefatos em .specify/bugs/<slug>/.

O fluxo principal é:

/speckit.bug.assess "Descreva o problema e a reprodução" slug=login-crash
/speckit.bug.fix slug=login-crash
/speckit.bug.test slug=login-crash

Em agentes como GitHub Copilot, a forma costuma ser com hífen, por exemplo:

/speckit-bug-assess "Descreva o problema e a reprodução" slug=login-crash
/speckit-bug-fix slug=login-crash
/speckit-bug-test slug=login-crash

Os comandos geram artefatos como:

.specify/bugs/login-crash/
├── assessment.md
├── fix.md
└── test.md

5. O que cada etapa faz

Assess

A etapa de assess é read-only em relação ao código fonte. Ela não modifica o código. O papel dela é:

  • triagem do relato do bug;
  • decidir se o problema é um bug real;
  • localizar a área do código suspeita;
  • propor uma remediação plausível.

Se o sistema recebe um bug report com stack trace ou issue, a etapa de assess usa isso como entrada. O resultado é um arquivo assessment.md que documenta a hipótese e a causa provável.

Fix

A etapa de fix é a única que edita código.

Ela aplica a correção descrita na assessment e registra o que foi alterado em fix.md. A documentação ressalta que a correção deve ficar dentro do escopo avaliado, e qualquer desvio precisa ser explicitado como “Deviation from Assessment”. Isso é importante porque evita correções que “aumentam o escopo” sem evidência.

Test

A etapa de test re-executa a reprodução e os testes relevantes. O resultado não é “simplesmente passou ou falhou”: a extensão usa três estados possíveis:

  • verified: tudo que foi necessário foi validado com sucesso;
  • partial: alguma verificação faltou ou não pode ser concluída;
  • failed: a correção ainda não resolveu o problema.

O ponto importante é que ela nunca “exagera” a evidência. Se a reprodução original não foi de fato exercitada, o resultado é downgrade para partial, mesmo que a suíte tenha passado.

6. Como ela resolve o problema

A extensão resolve um problema clássico da engenharia de software com IA: a tendência de tentar corrigir rápido antes de diagnosticar corretamente ou de validar sem evidência.

Ela introduz disciplina em três camadas:

  1. Rigor de diagnóstico: o agente primeiro investiga se o problema é real e qual é a causa provável.
  2. Escopo controlado: a correção é aplicada apenas sob a hipótese documentada.
  3. Evidência de verificação: a validação é reexecutada e registrada como prova, não como “parece que resolveu”.

Em outras palavras, ela transforma um bug em um fluxo de diagnóstico → reparo → prova.

7. Oficial x comunidade

Esta é uma extensão oficial do Spec Kit. Ela não é uma extensão da comunidade.

O texto oficial a descreve como bundled, opt-in extension, isto é, ela está disponível como parte do kit, mas precisa ser instalada explicitamente. Isso é diferente de uma extensão de terceiros listada no catálogo da comunidade, que exige revisão e costuma ser descoberta como “community extension”.

Então, a regra de classificação é simples:

  • Extensão oficial do Spec Kit: instalada com specify extension add bug e documentada no site oficial do projeto.
  • Extensão da comunidade: encontrada em catálogos externos/contribuídos e exigindo revisão antes de instalação.

8. Prática: quando vale usar?

Você tem uma falha real em produção ou em uma branch local. O bug é claro, a reprodução é reproducível e você precisa entregar correção com evidência. Qual fluxo faz mais sentido?

Use a extensão de bug fix. Se o objetivo é diagnosticar, corrigir e provar a correção sem “quebrar o escopo do trabalho”, esse fluxo é mais adequado do que abrir um novo processo de feature.
