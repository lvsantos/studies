Constitution: as regras que orientam o projeto

Vitória de hoje: saber quando usar /speckit-constitution e transformar regras reais do repositório em guardrails verificáveis.

A ideia central

A Constitution registra princípios que orientam todas as etapas seguintes do Spec Kit. Ela não descreve uma feature específica e não substitui documentação técnica: define limites e critérios que devem continuar verdadeiros enquanto o projeto evolui.

Execute-a normalmente uma vez no início do projeto e atualize-a quando os princípios compartilhados mudarem.

1. O que o comando faz

No GitHub Copilot, use:

/speckit-constitution Preserve public API compatibility. Require tests for behavior changes.

O comando cria ou atualiza .specify/memory/constitution.md. A documentação também mostra a forma com pontos, /speckit.constitution; a etapa é a mesma, mas esta integração usa skills com hífens.

A constituição é lida pelas etapas posteriores. Por isso, uma regra escrita aqui pode influenciar o plano técnico, a decomposição de tarefas e a revisão da implementação.

2. Escreva guardrails baseados em evidências

Em um projeto existente, não invente princípios para preencher o modelo. Antes de executar o comando, procure evidências em:

  • README.md e guias de contribuição;
  • decisões de arquitetura e documentação de APIs;
  • configurações de CI e comandos de teste;
  • restrições de compatibilidade, segurança ou implantação já assumidas pelo time.

Um guardrail bom é curto, observável e útil para decidir. “O código deve ser excelente” é vago. “Toda mudança de comportamento deve incluir testes automatizados” pode ser verificado durante a revisão.

Regra fracaGuardrail útil
Manter qualidade alta.Toda mudança de comportamento deve incluir ou atualizar testes automatizados.
Preservar o sistema.Alterações devem manter compatibilidade com os contratos públicos existentes.
Usar a arquitetura correta.Novas funcionalidades devem reutilizar os limites e padrões arquiteturais documentados.

3. O que a Constitution não faz

  • não cria uma especificação de feature;
  • não escolhe a stack ou a arquitetura de uma mudança específica;
  • não descreve retroativamente todo o comportamento existente;
  • não substitui testes, revisão de código ou documentação detalhada.

Ela funciona como uma camada de governança: as próximas decisões precisam respeitar os princípios ou explicar claramente por que uma alteração da própria constituição é necessária.

4. Pratique: encontre um princípio real

Imagine que o CI do projeto sempre executa testes unitários e de integração. Qual guardrail transforma essa evidência em uma regra útil?

“Toda mudança deve executar e passar nas suítes unitária e de integração estabelecidas pelo projeto.” A regra é observável e conecta a constituição a uma verificação que já existe.
