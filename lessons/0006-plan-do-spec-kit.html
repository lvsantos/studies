Plan: decidir como construir a feature

Vitória de hoje: transformar uma spec.md em um plano técnico coerente com a Constituição e com o repositório existente.

A ideia central

Specify responde “o que” e “por que”; Plan responde “como”. O comando parte da especificação e registra as decisões técnicas necessárias para implementá-la.

O plano não deve inventar uma arquitetura isolada. Ele pesquisa o repositório, reaproveita padrões existentes e torna as escolhas explícitas para as próximas etapas.

1. O que o comando faz

No GitHub Copilot, use a skill com hífens:

/speckit-plan Use a stack já existente no projeto e preserve os padrões atuais de testes e integração.

A documentação também mostra /speckit.plan. A forma depende do agente; a etapa é a mesma.

O resultado principal é plan.md. Dependendo da feature, o planejamento também pode produzir:

  • research.md para registrar descobertas e alternativas;
  • data-model.md para entidades e relações;
  • arquivos de contracts/ para interfaces ou APIs;
  • quickstart.md para orientar a validação da solução.

2. O que entra no plano

DecisãoPergunta
Contexto técnicoQual linguagem, plataforma, dependência e armazenamento já fazem sentido?
ArquiteturaEm quais módulos, serviços ou diretórios a mudança se encaixa?
Dados e contratosQuais entidades, esquemas, APIs ou interfaces serão criados ou alterados?
TestesQuais testes existentes e novos demonstram que a solução funciona?
RiscosQuais restrições, dependências e alternativas precisam ser registradas?

O plano deve explicar as escolhas, não apenas listar ferramentas. “Usar Postgres” é uma decisão incompleta; “reutilizar o Postgres já adotado pelo projeto para preservar o modelo de migrações existente” explica o motivo.

3. A verificação da Constituição

Antes da pesquisa e novamente depois do desenho técnico, o plano verifica os princípios do projeto. Essa etapa pergunta:

  • a solução respeita os guardrails definidos?
  • alguma decisão viola uma regra existente?
  • se houver uma exceção, ela está justificada?

Esse é o ponto de ligação entre as aulas: a Constitution estabelece limites, Specify descreve a mudança e Plan escolhe uma implementação dentro desses limites.

4. O que Plan não faz

  • não substitui uma especificação incompleta;
  • não deve decidir silenciosamente requisitos que ainda estão ambíguos;
  • não cria a lista final de tarefas, que pertence a tasks;
  • não implementa o código.

Se a equipe ainda discorda sobre o comportamento desejado, volte a clarify antes de escolher a solução técnica.

5. Pratique: escolha a instrução útil

Qual orientação ajuda o plan a produzir uma decisão técnica coerente?

  1. “Faça algo moderno e escalável.”
  2. “Use os padrões de API, testes e armazenamento já adotados pelo projeto; registre qualquer exceção.”

A segunda. Ela aponta para evidências do repositório e cria um critério para justificar desvios. A primeira é ampla demais para orientar uma decisão revisável.
