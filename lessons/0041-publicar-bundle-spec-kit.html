Publicar um bundle: release própria ou catálogo do Spec Kit

Vitória de hoje: validar e distribuir um setup por papel, sabendo quando basta publicar o pacote e como pedir sua inclusão no catálogo comunitário oficial.

Pacote, catálogo e curadoria são coisas diferentes

Seu repositório pode hospedar o bundle.yml, a documentação e o ZIP da release. Um catálogo controlado por você pode tornar esse bundle instalável por ID. Já o catálogo comunitário do Spec Kit é para descoberta: a submissão passa por um issue e por validação automatizada.

O bundles/catalog.json tem outra função: lista os bundles first-party que o projeto mantém. Não é um formulário de auto-publicação.

1. Defina o pacote como nas aulas anteriores

Um bundle reúne componentes que já têm suas próprias responsabilidades. Reaproveite as decisões das aulas de criação de extensão, criação de preset e criação de workflow: o bundle organiza versões e dependências, mas não substitui esses componentes.

Use os manifests de exemplo como referência de estrutura; os IDs demonstrativos não garantem que os componentes existam nos catálogos. Crie seu pacote e mantenha apenas o que o papel realmente precisa:

product-team/
├── bundle.yml
├── README.md
└── LICENSE

No bundle.yml, confira ID, nome, versão SemVer, papel, requisito mínimo do Spec Kit e cada componente declarado. Fixe as versões exigidas pelo formato. Uma referência no manifest não prova que o componente está publicado: confirme que ela resolve nos catálogos que o público terá disponíveis.

2. Valide e teste o ZIP de verdade

Validação e build respondem a perguntas diferentes: a primeira verifica estrutura e referências que podem ser verificadas; a segunda cria o artefato distribuível.

specify bundle validate --path ./product-team
specify bundle build --path ./product-team --output dist/
specify bundle install ./dist/product-team-1.0.0.zip

Faça a instalação em um projeto de teste limpo e confira os componentes instalados. Se o bundle depende de catálogos não padrão, adicione-os antes do teste e documente as URLs no README. O bundle distribui o manifest; componentes externos continuam precisando ser resolvidos nas fontes correspondentes. A referência de bundles detalha essa resolução.

3. Publique primeiro no seu repositório

Uma release versionada no seu GitHub já é uma forma completa de distribuição. Inclua o ZIP criado por bundle build, o bundle.yml, um README com papel, componentes, catálogos necessários e instruções, além da licença.

Quem receber o ZIP pode instalar pelo caminho do arquivo, sem esperar que o bundle apareça em um catálogo:

specify bundle install ./product-team-1.0.0.zip

Para instalar por ID dentro da organização, publique também um catálogo de bundles controlado por você e teste o fluxo completo:

specify bundle catalog add \
  https://acme.example/spec-kit/bundles.json \
  --id acme-bundles --policy install-allowed
specify bundle install product-team

A release hospeda o artefato; o catálogo aponta para ele. São duas peças que você mantém alinhadas. A lição de publicação de workflows usa a mesma distinção entre pacote e descoberta, mas o formato e os comandos são próprios de cada componente.

4. Peça entrada no catálogo comunitário

Para aparecer na busca comunitária do Spec Kit, publique a release no seu repositório e abra o formulário oficial de Bundle Submission. Ele pede, entre outros dados, ID e versão, URL do ZIP e do README, licença, requisito do Spec Kit, componentes, catálogos adicionais e evidência de teste em um projeto limpo.

  1. Confirme que validate e build passaram.
  2. Crie a release GitHub com o ZIP versionado e teste o arquivo baixado.
  3. Preencha o issue com metadados, dependências, exemplo de uso e testes.
  4. Aguarde a triagem: um mantenedor aplica o rótulo que inicia a validação automatizada.
  5. Corrija o que a validação apontar; após aprovação, a automação prepara a mudança no catálogo comunitário.

Não abra um PR editando bundles/catalog.community.json diretamente. O guia de contribuição determina o issue para novas entradas e atualizações; a automação gera o PR depois de validar release, links e metadados.

5. Não confunda catálogo comunitário com first-party

DestinoQuem mantémComo chegar
Seu repositório/releaseVocê ou sua equipePublique o ZIP; compartilhe o arquivo ou um catálogo próprio instalável.
bundles/catalog.community.jsonAutores independentes; entrada validada pelo processo comunitárioIssue Bundle Submission; não é instalação por ID no catálogo embutido padrão.
bundles/catalog.jsonProjeto Spec KitBundles first-party curados, como bugfix e assess; inclusão depende da decisão dos mantenedores.

O catálogo comunitário embutido é discovery-only: search e info ajudam a descobrir e inspecionar, mas não autorizam instalar pelo ID. A presença no catálogo não é auditoria de segurança nem endosso. Para uma contribuição first-party, siga a orientação dos mantenedores e o processo normal de contribuição; não use o formulário comunitário como atalho para catalog.json.

6. Pratique: qual caminho falta?

Seu bundle já tem uma release pública e uma colega instalou o ZIP. Ele ainda não aparece em specify bundle search no catálogo comunitário. Qual é a próxima ação correta?
