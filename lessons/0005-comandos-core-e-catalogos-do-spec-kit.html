Além do setup: extensões, presets e diagnóstico útil

Vitória de hoje: relembrar o mínimo do setup e aprender os comandos que tornam o fluxo mais útil sem repetir a mesma ideia da instalação inicial.

Resumo rápido do que já vimos

Dois comandos básicos já ficaram claros: uv tool install specify-cli instala o CLI e specify init --here --integration copilot prepara o projeto. Depois disso, o ambiente costuma ser validado com specify check e a versão com specify version. O importante é não confundir instalar com inicializar: o primeiro prepara o executável; o segundo prepara o projeto.

1. Quando o projeto precisa de mais “camadas”

Depois que o projeto já existe, nem sempre a próxima ação é “escrever uma feature”. Às vezes você quer deixar o ambiente mais útil, mais alinhado ao seu workflow ou mais explícito para a IA. Nessa zona entram as extensões e os presets.

Extensões

Extensões são módulos que adicionam comportamento ao Spec Kit. O caso mais importante aqui é a extensão de Git, que cria o suporte de branches e workflow de feature:

specify extension list
specify extension add git
specify extension remove git

Se a sua pergunta é “quero que o processo de feature fique mais organizado no Git?”, a extensão é a resposta. Ela não substitui a lógica de projeto; ela apenas conecta o Spec Kit ao seu fluxo de versionamento.

Quando a extensão vale a pena

  • quando você quer branch e feature mais explícitos;
  • quando o projeto precisa de rastreabilidade entre intenção e implementação;
  • quando sua equipe usa comandos de feature no mesmo estilo de fluxo de PR.

Em outras palavras, a extensão é útil quando o problema deixa de ser “o Spec Kit funciona?” e passa a ser “o Spec Kit conversa bem com o modo como meu time trabalha”.

2. Presets: reduzir a fricção do setup

Preset é um pacote de escolhas prontas para configurar um projeto. Em vez de você repetir uma decisão manual toda vez, o preset aplica uma configuração base já pensada.

specify preset list
specify preset add compliance
specify preset use compliance

O valor do preset não é “inventar um workflow”. Ele é “aplicar um conjunto de convenções que vocês já decidiram usar”. Isso é útil em equipes que querem manter regras e padrões constantes entre vários projetos.

Regra de bolso

Extensão resolve como o fluxo toca o Git. Preset resolve qual padrão inicial o projeto já deve seguir. Não são a mesma coisa, mas funcionam juntos quando você quer velocidade sem perder consistência.

3. Diagnóstico sem mexer no código

Às vezes a melhor ação não é criar ou alterar arquivos. É simplesmente verificar se o ambiente está forte o suficiente para seguir em frente.

specify integration status
specify integration list
specify integration info copilot

Esses comandos servem para responder perguntas como:

  • qual agente está ativo neste projeto?
  • houve alguma inconsistência na integração?
  • qual é a configuração atual do projeto e do agente?

Esse tipo de comando é valioso porque remove suposição. Em vez de “acho que o projeto está usando Copilot”, você confirma. Em vez de “talvez a integração esteja pronta”, você verifica o estado real.

4. Environment variables que fazem diferença

As variáveis de ambiente do Spec Kit são úteis quando você quer controlar o contexto do projeto sem depender de “dar um nome certo” manualmente. Elas parecem avançadas, mas a ideia é simples: elas descrevem onde está o projeto e qual feature está ativa.

VariávelFunção principalQuando usar
SPECKIT_INTEGRATION_DEFAULTDefine a integração padrão usada quando o comando specify init não recebe --integration.Em sessões headless, CI ou quando você quer padronizar o agente sem digitar o argumento explicitamente.
SPECIFY_INIT_DIRDefine a pasta do projeto que o Spec Kit deve resolver, útil em monorepos ou quando o projeto não está no diretório atual.Quando você quer apontar para um projeto em outro diretório sem fazer cd.
SPECIFY_FEATURE_DIRECTORYDefine a feature ativa dentro do projeto, sobrescrevendo o valor em .specify/feature.json.Quando você precisa selecionar uma feature fora do fluxo normal de uso.
SPECIFY_FEATUREDefine o rótulo da feature que o shell/ajuda do Spec Kit deve reportar.Em scripts, automação e shell customizado, especialmente quando o fluxo não depende do Git para identificar o estado.
SPECKIT_INTEGRATION_CATALOG_URLDefine um catálogo de integrações alternativo para a resolução de agentes e plugins.Quando você quer usar um catálogo externo ou personalizado em vez do catálogo padrão.

O detalhe mais importante é que o Spec Kit separa dois tipos de contexto:

  1. Projeto: definido por SPECIFY_INIT_DIR e pela pasta que contém .specify/;
  2. Feature ativa: definida por SPECIFY_FEATURE_DIRECTORY ou por .specify/feature.json.

Essa separação evita um erro comum: achar que “o branch atual” é a única fonte de verdade. O comando e o projeto têm um estado lógico próprio, e as variáveis ajudam a controlar esse estado de maneira previsível.

Na prática, você normalmente não precisa definir todas essas variáveis no dia a dia. Mas quando o ambiente fica menos direto — monorepo, scripts, CI, vários projetos em paralelo — elas passam a ser uma ferramenta muito útil para evitar confusão.

NOTE · Por que feature.json fica fora do Git?

O Spec Kit mantém o estado da feature em .specify/feature.json fora do Git por uma razão de contexto, não de segurança. Esse arquivo descreve qual feature está ativa no projeto em um dado momento; ele é um ponteiro local de trabalho, não uma regra de negócio do projeto.

Se ele fosse versionado, cada pessoa, máquina ou branch acabaria “puxando” um estado de feature diferente e isso conflitaria com a ideia de que a feature ativa deve ser uma escolha local do ambiente atual. O Git cuida do código e dos artefatos compartilhados; o arquivo feature.json ajuda o Spec Kit a saber em qual contexto cada pessoa está trabalhando agora.

Por isso, a documentação do projeto também deixa esse estado em um espaço que fica fora do controle de versionamento compartilhado, junto com outros arquivos de máquina-local e infraestrutura do tooling. O objetivo é separar o “estado de execução do fluxo” do “estado produto do repositório”.

5. O “molde” mental que vale guardar

Depois dessa viagem, o mapa fica assim:

  • Instalação: uv tool install specify-cli e specify version.
  • Projeto: specify init --here --integration copilot.
  • Fluxo de feature: specify, plan, tasks, implement.
  • Ambiente e suporte: extension, preset, integration status.

É fácil achar que “o Spec Kit é só sobre especificações”. Mas o que o torna confiável na prática é a camada de infraestrutura: projeto correto, agente correto, extensão correta e diagnóstico correto.

Prática rápida

Sem olhar a documentação, responda em voz alta: “Se eu quiser confirmar se a integração do projeto está saudável sem alterar arquivos, qual comando usar?”

specify integration status. Esse comando faz uma verificação do estado atual da integração do projeto e ajuda a detectar inconsistências antes de você iniciar uma nova feature.
