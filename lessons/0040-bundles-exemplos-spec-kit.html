Bundles por papel: leia o manifest sem confundi-lo com catálogo

Vitória de hoje: comparar quatro composições exemplificativas e detectar o que precisa existir nos catálogos antes de tratá-las como instaláveis.

Importante: são apenas exemplos

Os diretórios em examples/bundles são manifests e READMEs para demonstrar como empacotar uma configuração por papel. Não são os bundles first-party publicados no catálogo instalável e não devem ser descritos como bundles oficiais prontos para instalar por ID. O catálogo first-party contém assess e bugfix; compare com as lições 38 e 39.

1. O padrão que os exemplos demonstram

Os quatro manifests compartilham schema 1.0, versão do bundle 1.0.0, autor spec-kit-examples, licença MIT, requisito Spec Kit >=0.9.0 e nenhuma ferramenta/MCP adicional declarada. Todos são agnósticos à integração: herdam a integração ativa do projeto.

2. O que acontece na instalação?

O bundle entrega o manifesto, não necessariamente os arquivos/payloads de cada componente. O CLI lê provides, expande as dependências, verifica versões e integração, e encaminha cada item ao instalador de extension, preset, step ou workflow. As versões de extension/preset/workflow estão fixadas nos manifests acima; os steps não declaram versão ali e são resolvidos exclusivamente por catálogos de steps.

Por isso, nomes como requirements-elicitation ou secure-sdd são referências declaradas, não prova de que esses pacotes estão publicados ou presentes no clone. Se as origens ativas não fornecerem um componente, a validação não pode garantir a instalação. Um bundle ZIP local também não embute automaticamente dependências externas.

Este modelo de composição lembra o exemplo business-analyst da lição 36, mas aqui estão listados os quatro manifests atuais. Em contraste, a lição 37 cobre itens submetidos a catálogo comunitário: descoberta comunitária e exemplos no repositório são categorias diferentes.

3. Validar e empacotar como autor

Use o clone do repositório do Spec Kit para validar um manifest e gerar seu artefato:

specify bundle validate --path examples/bundles/developer
specify bundle build --path examples/bundles/developer --output dist/

A validação verifica estrutura e referências usando componentes incluídos/instalados e catálogos alcançáveis; referências impossíveis de verificar podem virar avisos. O build gera um ZIP versionado com o manifest. Antes de instalar o artefato, confirme que todos os IDs apontam para releases existentes, que os catálogos necessários estão configurados e que o resultado corresponde ao papel pretendido.

Para um caso real, revise especialmente a precedência: no exemplo security-researcher o preset usa priority 5, antes dos presets de prioridade maior. A estratégia append acrescenta orientação em vez de substituir a camada inferior. Compare estratégias com o scaffold de presets.

4. Pratique: exemplo ou bundle oficial?

Um arquivo examples/bundles/developer/bundle.yml existe no repositório e descreve um setup completo. Isso basta para concluir que specify bundle install developer funciona pelo catálogo first-party?
