Criar um workflow próprio: da sequência ao YAML

Vitória de hoje: transformar um processo que você já repete em uma definição testável, com entradas explícitas e revisão no ponto certo.

Workflow não é extensão nem preset

Use um workflow quando o que falta é definir em que ordem etapas existentes acontecem e onde o processo deve parar para uma decisão humana. Uma extensão fornece comandos ou integração que ainda não existem; um preset adapta comandos ou templates existentes. Consulte também as aulas sobre criar extensão e criar preset.

O exemplo desta aula executa specify, pausa para revisar a spec e só então chama plan. Ele usa comandos e tipos de etapa já fornecidos pelo Spec Kit.

1. Desenhe o processo antes do arquivo

Escreva a sequência em linguagem simples e responda cinco perguntas:

  1. Qual é o resultado? Criar uma spec e um plano para uma feature.
  2. Quais dados entram? Uma descrição da feature e a integração a usar.
  3. Quais passos são necessários? Chamar speckit.specify e depois speckit.plan.
  4. Onde uma pessoa precisa decidir? Depois de ler a spec e antes do plano.
  5. Quais são os pré-requisitos? Projeto inicializado e uma versão do Spec Kit compatível.

Esse desenho pequeno já vira um workflow útil. Comece pelas etapas que mudam o resultado; não adicione loops, shell ou branches só porque o motor os suporta.

2. Declare identidade, entradas e etapas

Crie workflow.yml. O ID identifica o workflow, a versão segue SemVer e cada etapa recebe um ID único. Este exemplo requer Spec Kit >=0.8.5, que resolve integration: auto para a integração inicializada no projeto:

schema_version: "1.0"

workflow:
  id: "feature-review"
  name: "Feature Review"
  version: "0.1.0"
  author: "Sua equipe"
  description: "Gera uma spec, pede revisão e cria o plano"

requires:
  speckit_version: ">=0.8.5"

inputs:
  spec:
    type: string
    required: true
    prompt: "O que você quer construir?"
  integration:
    type: string
    default: "auto"

steps:
  - id: specify
    command: speckit.specify
    integration: "{{ inputs.integration }}"
    input:
      args: "{{ inputs.spec }}"
  - id: review-spec
    type: gate
    message: "Revise a spec antes de continuar para o plano."
    options: [approve, reject]
    on_reject: abort
  - id: plan
    command: speckit.plan
    integration: "{{ inputs.integration }}"
    input:
      args: "{{ inputs.spec }}"

Os valores de entradas e as saídas de etapas anteriores podem ser referenciados com expressões como {{ inputs.spec }}. Um gate pausa a execução para revisão; approve libera o próximo passo e reject encerra este run. A definição, não o gate, determina o que acontece em cada resposta.

3. Valide no projeto de laboratório

Em um projeto iniciado com specify init, primeiro peça ao CLI para inspecionar o YAML e depois rode uma execução real:

specify workflow info ./workflow.yml
specify workflow run ./workflow.yml \
  --input spec="Adicionar exportação CSV ao histórico de ordens" \
  --input integration=copilot

Quando o gate pausar, leia a spec gerada antes de aprovar. Confira o estado e retome o mesmo run:

specify workflow status <run_id>
specify workflow resume <run_id>

Teste também a rejeição. O resultado esperado é o run abortado antes de plan, não uma revisão automática nem a remoção dos arquivos que specify já criou. A validação de info confere a definição; não substitui o teste das etapas com a integração que você pretende suportar.

4. Revise o contrato antes de compartilhar

  • IDs do workflow e das etapas são estáveis e únicos; entradas obrigatórias, padrões e opções estão claros.
  • Pré-requisitos e integrações declarados correspondem ao que você testou.
  • Expressões só apontam para entradas ou etapas anteriores.
  • Gates explicam o que revisar e o significado de aprovar/rejeitar.
  • O README explica propósito, entradas, etapas, limitações e compatibilidade.
Segurança do YAML

Um step shell executa comandos locais com os privilégios do usuário, sem sandbox. Valores interpolados em run não recebem escape automático. Evite shell se um step declarativo resolve o caso; se for indispensável, limite os valores aceitos, explique a operação no README e revise exatamente o YAML que será distribuído.

5. Pratique: encontre a fonte da verdade

Você pretende publicar a versão 1.0.0, mas o YAML local ainda declara workflow.version: "0.9.0". Antes de criar a tag e a release, qual arquivo e campo você atualiza?
