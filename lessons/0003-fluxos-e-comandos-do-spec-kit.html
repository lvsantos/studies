Escolher o caminho do Spec Kit

Vitória de hoje: distinguir o Shorter path do Full path e reconhecer o papel de cada comando antes de estudá-lo em profundidade.

A ideia central

Os dois caminhos começam com uma especificação e terminam com implementação e verificação. O Full path acrescenta pontos de revisão para features mais arriscadas. A constituição do projeto é uma preparação feita uma vez, antes do caminho escolhido.

1. Dois caminhos

FluxoQuando usarSequência
Shorter pathFeature pequena, clara e de baixo risco.specify → plan → tasks → implement → converge
Full pathFeature de produção, ambígua ou com maior impacto.specify → clarify → plan → checklist → tasks → analyze → implement → converge

O caminho curto economiza etapas quando o risco é pequeno. O caminho completo investe em esclarecer requisitos e conferir a qualidade dos artefatos antes de construir.

2. Os nove comandos, em uma frase

  1. Constitution: registra os princípios e limites compartilhados do projeto.
  2. Specify: transforma uma necessidade em usuários, cenários e requisitos.
  3. Clarify: resolve ambiguidades antes que elas contaminem o plano.
  4. Plan: escolhe a abordagem técnica para atender à especificação.
  5. Checklist: cria uma revisão da qualidade dos requisitos.
  6. Tasks: quebra o plano em tarefas ordenadas por dependência.
  7. Analyze: procura conflitos e lacunas entre spec, plan e tasks.
  8. Implement: executa as tarefas e valida o que foi construído.
  9. Converge: compara o resultado com os artefatos e registra o que falta.

No GitHub Copilot, as skills aparecem com hífens, como /speckit-specify. Algumas referências usam pontos, como /speckit.specify; a etapa é a mesma. A documentação do processo recomendado e o resumo oficial dos comandos mostram as duas convenções.

3. Pratique

Você recebeu uma ideia vaga para uma feature de produção. Qual é a primeira etapa específica da feature?

/speckit-specify. Primeiro descreva a necessidade. Depois, use clarify se ainda houver ambiguidades antes de planejar.
