Workflow comunitário: descubra, inspecione, decida

Vitória de hoje: distinguir os catálogos de workflows e de steps, e avaliar uma sequência comunitária antes de executá-la com Copilot.

Não confunda catálogo com aprovação

Assim como no catálogo de extensions comunitárias, o catálogo comunitário de workflows é uma fonte de descoberta, não um selo de confiança. O CLI deixa pesquisar e inspecionar os itens, mas o catálogo comunitário padrão não permite instalar pelo ID. Os autores mantêm o código; a presença no catálogo não significa que o workflow foi auditado ou endossado.

Isso difere do fluxo de presets comunitários, cujo comando de instalação por ID não deve ser presumido para workflows. Aqui, a configuração dos catálogos controla se uma origem pode instalar.

1. Dois catálogos, duas coisas diferentes

Os arquivos catalog.json e catalog.community.json listam workflows completos: sequências de comandos, gates e outras etapas. Os arquivos step-catalog.json e step-catalog.community.json listam tipos de step reutilizáveis, isto é, comportamento novo que um YAML pode chamar com type:.

Na consulta de 26/09/2026, o catálogo de workflows da comunidade lista pipeline e yolo. Os dois catálogos de steps, oficial e comunitário, têm "steps": {}: não há step types publicados neles nesse momento. Um step comunitário futuro merece revisão especialmente cuidadosa: seu pacote inclui Python que o CLI importa ao carregar o step.

2. Descubra sem instalar

Em um projeto inicializado, veja as origens ativas, pesquise e peça a ficha do item:

specify workflow catalog list
specify workflow search --tag automation
specify workflow info pipeline

A busca inclui os catálogos ativos, por padrão o oficial e o comunitário. A ficha ajuda a comparar versão, autor, requisitos, entradas e etapas; ela não substitui a leitura do YAML real, do README e dos arquivos auxiliares versionados.

3. Compare o processo real

ExemploO que prometeO que verificar
pipeline 1.1.0Clarify, análise antes de implementar e um loop limitado de converge + implement; aceita Copilot e requer Spec Kit 0.11.2 ou superior.Tem um gate após clarify, mas não os gates de revisão da spec e do plan do workflow oficial speckit. O nome “Guided” não garante esses checkpoints.
yolo 0.1.0Specify → plan → tasks → implement sem interrupções entre as etapas.Remove todos os gates. Além disso, a ficha do catálogo declara requisito mínimo 0.8.12, enquanto o README/YAML versionado declara 0.8.5: esclareça a divergência antes de usar.

Em ambos, examine os comandos chamados, os tipos de step, os gates, dependências de extensions, requisitos de versão e qualquer shell ou interpolação. Shell roda com os privilégios locais; a validação estrutural do YAML não é auditoria de segurança.

4. Depois da revisão, escolha a origem

Se o projeto ou a equipe decidir instalar o item revisado, use uma URL HTTPS versionada. O CLI pede confirmação ao instalar de uma URL externa não registrada em catálogo:

specify workflow add pipeline --from https://raw.githubusercontent.com/domattioli/spec-kit-workflow-pipeline/v1.1.0/workflow.yml
specify workflow list
specify workflow run pipeline --input spec="Descreva a feature"

Outra opção é a equipe publicar um catálogo próprio e marcar explicitamente a origem como instalável segundo sua política. Não transforme o catálogo comunitário de descoberta em fonte instalável por conveniência. Depois, confira as etapas instaladas e acompanhe pausas com specify workflow status e specify workflow resume <run_id>.

5. Pratique: qual sequência serve?

Você quer usar Copilot, revisar a spec antes do plan e revisar o plan antes de gerar tasks. A ficha de um workflow diz “Guided SDD Pipeline”. Isso basta para instalá-lo?
