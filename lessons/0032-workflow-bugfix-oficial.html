bugfix: diagnosticar antes de tocar no código

Vitória de hoje: entender por que a revisão aparece antes da correção e por que workflow concluído não significa bug verificado.

Quando escolher

Use bugfix para comportamento existente que está quebrado. Se ainda está decidindo se uma ideia vale ser construída, use assess; se a decisão de construir já está tomada, use speckit.

Inputs e pré-requisitos

O workflow requer Spec Kit >=0.9.0 e a extensão oficial opt-in bug, que fornece os comandos speckit.bug.*.

InputObrigatório?Uso
reportSimRelato colado ou URL do bug/issue.
slugSimIdentificador curto, como login-empty-password.
integrationNãoPadrão auto; pode ser copilot se essa for a integração ativa.
 
specify extension add bug
specify workflow run bugfix \
  --input report="Login com senha vazia termina em erro 500; esperado: mensagem de validação" \
  --input slug=login-empty-password \
  --input integration=copilot

Etapas, artefatos e gate

  1. assess: investiga se o relato é bug, localiza caminhos suspeitos e propõe remediação. Não altera o código-fonte.
  2. review-assessment: gate approve/reject antes de qualquer mudança de código.
  3. fix: aplica a remediação documentada e registra mudanças. É a única etapa deste trio que altera código.
  4. test: roda a reprodução e testes relevantes, registrando evidências.

Os relatórios ficam em .specify/bugs/<slug>/: assessment.md, fix.md e test.md. Use o mesmo slug nas três etapas para manter o diagnóstico, patch e validação ligados.

Como o gate reage

Approve: libera fix e em seguida test, na mesma execução. Não há outro gate oficial depois do patch. Portanto, revisar o diff e o relatório final continua sendo responsabilidade sua.

Reject: o YAML usa on_reject: abort. A execução para antes de editar código. Isso não reescreve assessment.md, não chama o agente para uma segunda hipótese e não tenta novamente o gate sozinho. Se a execução ficou pausada, workflow status e workflow resume <run_id> continuam o run; se o gate foi rejeitado, ele foi abortado, não “reprovado para retry”.

A extensão também protege relatórios existentes contra sobrescrita silenciosa. Corrija ou descarte explicitamente o diagnóstico, e não reutilize um slug existente como se ele fosse uma pasta temporária.

Resultado do teste não é status do workflow

Resultado em test.mdInterpretaçãoPróximo passo
verifiedA reprodução e os requisitos de verificação foram exercitados com sucesso.Revisar patch e evidências antes de integrar.
partialAlguma evidência/reprodução não pôde ser concluída.Fornecer o ambiente ou dado faltante e verificar novamente.
failedA verificação encontrou problema ainda presente.Revisitar diagnóstico/correção com a evidência e testar de novo.

O comando test pode registrar um resultado de domínio sem falhar como etapa de execução. Logo, workflow status em completed quer dizer que a sequência terminou, não que test.md diz verified. A definição oficial não contém um loop automático fix → test → fix.

Exemplo de decisão

O relato diz que senha vazia produz HTTP 500. assessment.md aponta outra causa sem reproduzir o cenário. Não aprove só porque o arquivo existe: rejeite/pare antes do patch e peça evidência ou corrija o diagnóstico. Se aprovar, acompanhe as mudanças em fix.md, depois leia test.md e compare o resultado ao sintoma original.

Prática de recuperação

O workflow terminou com estado completed, mas test.md diz partial porque a reprodução não rodou. O bug está verificado?
