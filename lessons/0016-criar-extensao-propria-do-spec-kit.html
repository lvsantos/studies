Criar uma extensão própria do Spec Kit

Vitória de hoje: entender o mínimo necessário para transformar uma automação útil em uma extensão reutilizável e instalarável em qualquer projeto Spec Kit.

O mapa mental

Uma extensão não é um “script solto”. Ela é um pacote com manifesto, comandos, configuração e regras de publicação/instalação.

O ponto central: você cria uma extensão quando quer que o Spec Kit reconheça novos comandos e hooks em projetos diferentes.

1. Quando vale criar uma extensão própria?

Crie uma extensão quando a automação for:

  • reutilizável em mais de um projeto;
  • ligada a uma ferramenta externa ou fluxo interno da empresa;
  • melhor expressa como comando do agente, e não como shell script manual;
  • algo que quer distribuir por catálogo, URL ou repositório interno.

Se a “solução” for só para um único projeto, muitas vezes o melhor custo-benefício é um script local ou um preset. Se ela precisa ser instalada, encontrada e reutilizada, o modelo certo é uma extensão.

2. Estrutura mínima

O mínimo prático é assim:

my-ext/
├── extension.yml
├── README.md
├── LICENSE
├── commands/
│   └── hello.md
├── scripts/
│   └── helper.sh
└── .extensionignore

A extensão precisa de um arquivo de manifesto, e o padrão oficial exige que ele seja válido e siga semver.

3. O manifesto é o “contrato” da extensão

O arquivo extension.yml define identidade, compatibilidade, comandos e configuração. O modelo mínimo costuma ser assim:

schema_version: "1.0"

extension:
  id: "my-ext"
  name: "My Extension"
  version: "1.0.0"
  description: "My custom extension"
  author: "Seu Nome"
  repository: "https://github.com/voce/spec-kit-my-ext"
  license: "MIT"

requires:
  speckit_version: ">=0.1.0"

provides:
  commands:
    - name: "speckit.my-ext.hello"
      file: "commands/hello.md"
      description: "Say hello"
      aliases: ["speckit.my-ext.hi"]

O mais importante aqui é a regra de nomenclatura: cada comando deve seguir o padrão speckit.{extension-id}.{command}.

4. Cada comando é um arquivo Markdown

Uma extensão expõe comando como um arquivo em Markdown, com frontmatter e corpo em instruções. O modelo é simples e universal:

---
description: "Say hello command"
tools:
  - 'some-tool/function'
---

# Hello Command

## User Input

$ARGUMENTS

## Steps

1. Greet the user
2. Show extension is working

```bash
echo "Hello from my extension!"
echo "Arguments: $ARGUMENTS"
```

A parte técnica interessante é que o Spec Kit reescreve caminhos e registra o comando para o agente certo, seja Claude, Copilot, Gemini ou outro suporte fornecido pelo projeto.

5. Configuração e camada de resolução

Extensões normalmente vêm com configuração em layers:

  1. defaults do próprio manifesto;
  2. config do projeto em .specify/extensions/my-ext/my-ext-config.yml;
  3. override local, se existir;
  4. variáveis de ambiente do tipo SPECKIT_MY_EXT_*.

Isso é importante porque a extensão deve ser fácil de usar em times diferentes sem duplicar arquivos ou colar segredos dentro do repositório.

6. Como testar localmente

O fluxo oficial de desenvolvimento é usar a instalação local:

specify extension add --dev /caminho/para/minha-extensao

Depois disso, verifique:

specify extension list

O comando deve mostrar a extensão e os comandos que ela registrou. Em seguida, teste a execução do agente com o comando novo, por exemplo:

/speckit.my-ext.hello mundo

Se o comando aparecer e funcionar, você já validou o ciclo básico de criação e instalação.

7. O que a extensão ganha ao ser “de verdade”

Uma extensão bem feita pode:

  • registrar comandos no agente;
  • injetar hooks em eventos do workflow, como after_tasks ou after_implement;
  • carregar scripts e templates;
  • ser distribuída por catálogo, por URL ou em um repositório privado.

Isso é a diferença entre “um script utilitário” e um “mecanismo de workflow do Spec Kit”.

8. Dicas importantes

  • use ID em minúsculas e hífens: my-ext, não MyExt;
  • use versionamento semver: 1.0.0;
  • não commite segredos: use variáveis de ambiente;
  • crie uma README e uma LICENSE antes de publicar;
  • evite acoplar a extensão a um único projeto. Faça-a genérica o suficiente para justificar ser extensão.
