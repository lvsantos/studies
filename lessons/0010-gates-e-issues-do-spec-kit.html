Os comandos de revisão e acompanhamento

Vitória de hoje: saber quando usar clarify, checklist, analyze e taskstoissues sem confundir seus papéis.

A ideia central

Os três primeiros comandos são portões de qualidade que você adiciona quando a feature tem ambiguidade, risco ou necessidade de revisão. O quarto não revisa os artefatos: transforma tarefas em issues do GitHub para acompanhar a execução.

Uma sequência comum para uma feature de produção é clarify → plan → checklist → tasks → analyze. Os portões são deliberados; não precisam aparecer em toda mudança pequena.

1. Clarify: resolver ambiguidades

No GitHub Copilot:

/speckit-clarify

Clarify faz perguntas direcionadas sobre a especificação atual e incorpora as respostas em spec.md. Ele é útil quando uma expressão como “arquivo legível”, “acesso permitido” ou “resposta rápida” ainda admite interpretações diferentes.

Use-o antes do plan quando uma decisão de comportamento puder mudar a solução técnica. Se a dúvida revelar um requisito errado ou incompleto, volte ao specify.

2. Checklist: testar a qualidade dos requisitos

/speckit-checklist

Um checklist é como um teste unitário escrito em linguagem natural: verifica se os requisitos são claros, completos, consistentes e cobrem os casos importantes.

Ele não testa se o código funciona. Pergunta, por exemplo, se a spec define estados de erro, regras de permissão ou comportamento para cada cenário.

Quem revisa e quem decide?

A IA pode gerar o checklist e, se você pedir explicitamente, ajudar a avaliar cada item. Mas um checklist personalizado é do revisor humano: a pessoa ou o time decide se o requisito está claro, completo e consistente e então marca o item como [x].

O checklist está completo quando todos os critérios relevantes foram revisados e aprovados pelo responsável. Isso significa “os requisitos têm qualidade suficiente para seguir”, não “o código já foi implementado”. Itens não marcados continuam sendo lacunas de especificação.

Há também um checklist embutido de requisitos, mantido por specify e clarify. Ele acompanha a spec, mas a aprovação de um checklist personalizado continua sendo responsabilidade do revisor.

Portanto, no exemplo desta aula, depois de clarify a IA pode propor perguntas sobre permissões e erros; o usuário ou o revisor do time verifica se as respostas realmente cobrem os cenários e decide quando os itens estão satisfeitos.

O arquivo e o momento

O comando cria um arquivo dentro da pasta ativa da feature:

specs/001-exportar-estudos/checklists/requirements.md
specs/001-exportar-estudos/checklists/security.md
specs/001-exportar-estudos/checklists/ux.md

O checklist embutido requirements.md é criado ou mantido por specify e clarify. Já /speckit-checklist cria um checklist personalizado com um nome curto, como security.md, api.md ou ux.md. Se o arquivo já existir, a IA acrescenta novos itens sem apagar os anteriores.

Gere-o depois que a spec.md estiver suficientemente descrita e, em geral, antes de tasks. O revisor lê os itens, responde às lacunas na spec e marca [x] apenas quando considera o requisito satisfatório. Novos itens gerados continuam como [ ].

Exemplos de pedidos ao agente:

/speckit-checklist Focus on permissions, unauthorized access, and data exposure.
/speckit-checklist Focus on API error responses, compatibility, and versioning.
/speckit-checklist Focus on loading, empty, error, and keyboard-accessible states.

Esses pedidos podem gerar, respectivamente, checklists de segurança, API e UX. A IA propõe os critérios; o revisor decide se cada critério está coberto pela especificação.

3. Analyze: conferir a consistência dos artefatos

/speckit-analyze

Analyze compara spec.md, plan.md e tasks.md depois que as tarefas foram geradas. Ele procura conflitos, lacunas, duplicações e tarefas sem requisito correspondente.

É uma análise somente leitura. Se encontrar um problema, corrija o artefato que possui a decisão e rode a análise novamente antes de implementar.

ComandoObjeto da revisãoModifica arquivos?
clarifyAmbiguidades da specSim, registra respostas em spec.md
checklistQualidade dos requisitosGera checklist para revisão humana
analyzeConsistência entre spec, plan e tasksNão, produz relatório

4. Taskstoissues: levar tarefas para o GitHub

/speckit-taskstoissues

Esse comando converte as tarefas existentes em issues acionáveis, preservando o ID da tarefa no título para facilitar o rastreamento. Ele é opcional e exige um remoto origin apontando para um repositório GitHub.

Antes de criar issues, o comando procura IDs já existentes para evitar duplicação. Ele não substitui tasks.md nem implementa as tarefas: apenas cria uma camada externa de acompanhamento.

Regra de segurança

Se o remoto não for uma URL do GitHub, não crie issues. Confirme também se você quer transformar toda a lista de tarefas em acompanhamento externo antes de executar o comando.

6. Pratique: diferencie os portões

A spec diz “exportar em formato legível”, mas não define qual formato. Depois de esclarecer isso, você quer verificar se todas as regras de permissão e erro foram descritas. Quais comandos usar?

clarify primeiro e checklist depois. O primeiro resolve a ambiguidade e atualiza a spec; o segundo revisa se os requisitos ficaram completos e claros.
