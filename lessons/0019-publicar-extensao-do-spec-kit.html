Publicar uma extensão em catálogo próprio ou da comunidade

Vitória de hoje: entender como uma extensão deixa de ser “local” e vira algo compartilhável, governável e instalável por outras pessoas.

O mapa mental

Há três caminhos principais:

  • instalação por URL direta para uso ad hoc;
  • catálogo próprio / privado para times e organizações;
  • catálogo da comunidade para descoberta pública, revisão e compartilhamento.

A diferença crucial é: descoberta e instalação não são a mesma coisa.

1. O que significa “publicar” em Spec Kit

Publicar uma extensão não significa apenas “colocar no GitHub”. A parte importante é garantir que outras pessoas consigam:

  1. encontrar a extensão;
  2. ver requisitos e compatibilidade;
  3. instalar em um projeto com specify extension add;
  4. entender se ela vem de um catálogo aprovado ou de um catálogo de descoberta.

Em Spec Kit, o projeto documenta explicitamente a ideia de catalog stack: há um catálogo principal de instalações aprovadas e um catálogo de comunidade para descoberta, não para instalação direta.

2. O catálogo da comunidade é de descoberta, não de instalação direta

Esse é o ponto mais importante para não cair em confusão. O README oficial deixa claro que:

  • o catálogo de comunidade serve para explorar extensões públicas;
  • ele é uma referência de descoberta;
  • a instalação direta a partir dele normalmente não é permitida sem passar por uma catalogação aprovada.

Em termos práticos, o fluxo é:

  1. busca na comunidade;
  2. avalia qualidade, risco e compatibilidade;
  3. copia a entrada para um catálogo próprio com install_allowed: true;
  4. instala com o nome da extensão.

3. Catálogo próprio: para time ou organização

Quando você controla o ambiente de um time, o catálogo próprio é o mecanismo mais seguro e previsível.

Você cria um arquivo catalog.json com suas extensões aprovadas e o aponta em um repositório interno ou público da organização. Depois, o projeto usa esse catálogo como a fonte de verdade para instalação.

O comando oficial é:

specify extension catalog add \
  --name "internal" \
  --priority 2 \
  --install-allowed \
  https://internal.company.com/spec-kit/catalog.json

Depois, a busca e a instalação viram um processo de catálogo aprovado e governado, em vez de improviso por URL aleatória.

4. Instalação por URL direta

Há uma opção para uso ad hoc ou desenvolvimento:

specify extension add meu-ext --from https://github.com/voce/spec-kit-meu-ext/archive/refs/tags/v1.0.0.zip

Essa opção serve para:

  • testar uma extensão antes de aprovar a entrada no catálogo;
  • usar uma extensão privada ou experimental;
  • instalar uma versão em desenvolvimento localmente.

Mas ela é uma exceção, não o modelo preferido para compartilhamento em equipe.

5. Como publicar no catálogo da comunidade

O guia oficial pede um fluxo de release e publicação explícito.

  1. crie um repositório com a extensão;
  2. valide o extension.yml;
  3. crie release do GitHub com tag semver;
  4. arquivo um issue de submissão no repositório do Spec Kit, usando o template de extensão;
  5. aguarde a revisão e a entrada no catalog.community.json.

O processo não pede um PR direto para o catálogo da comunidade. A documentação indica que a entrada é revisada via issue e depois integrada por um mantenedor.

6. Checklist antes da publicação

Antes de subir para o catálogo, confirme:

  • o extension.yml está válido;
  • o ID é minúsculo com hífens;
  • o número de versão está em semver;
  • o repositório e o arquivo de release existem;
  • a README explica instalação, uso e configuração;
  • existe LICENSE, CHANGELOG e comandos funcionando.

Sem esse conjunto, a extensão pode não ser instalável ou pode gerar risco real para quem instalar.

7. Como a equipe usa isso em produção

O fluxo recomendado para organizações costuma ser:

  1. descobrir extensões na comunidade;
  2. revisar o código, documentação e compatibilidade;
  3. copiar as entradas aprovadas para o catálogo interno;
  4. manter um catálogo governado e consistente.

Isso mantém o ambiente previsível: a comunidade é fonte de descoberta, mas a organização decide o que é apto para instalação.

8. Regra de ouro

Não pense em “catalog community = install direto”. Isso é o erro clássico aqui.

O padrão oficial do Spec Kit é:

  • descoberta pública → catálogo da comunidade;
  • instalação aprovável → catálogo próprio ou catálogo de organização;
  • uso ad hoc → URL direta ou instalação local em desenvolvimento.
Fonte primária

Use o README de Extensions, o Extension Publishing Guide, o Extension User Guide e o RFC Extension System. Juntos, eles mostram a política de descoberta, governança e publicação do sistema.
