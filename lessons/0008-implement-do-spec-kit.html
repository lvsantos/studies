Implement: executar o plano com controle

Vitória de hoje: entender como o agente transforma tasks.md em código, valida cada etapa e sabe quando parar.

A ideia central

Implement não decide o que construir nem cria a ordem do trabalho. Ele executa as tarefas já definidas, respeitando o plano, as dependências e os critérios do projeto.

O comando é a passagem dos artefatos para o código, mas continua sendo um processo revisável: cada fase deve ser validada antes da próxima.

1. Antes de implementar

No GitHub Copilot, use a skill com hífens:

/speckit-implement

A documentação também mostra /speckit.implement. A forma depende do agente; a etapa é a mesma.

Antes de executar, o agente lê o contexto da feature:

  • spec.md para a intenção e os requisitos;
  • plan.md para arquitetura e decisões técnicas;
  • tasks.md para a ordem concreta do trabalho;
  • Constitution e artefatos auxiliares, quando existirem.

2. Checklist é um gate

Se a feature tiver checklists, o comando verifica o estado deles antes de construir. Itens não marcados indicam que a qualidade dos requisitos ainda não foi aprovada.

O agente deve informar a situação e pedir confirmação antes de prosseguir quando houver itens pendentes. Ele não deve marcar o checklist por conta própria: a aprovação da qualidade pertence ao revisor.

Essa regra evita que uma lista de requisitos ainda incompleta seja tratada como autorização silenciosa para implementar.

3. Execute por fases

  1. Setup: prepara estrutura, dependências e configurações iniciais.
  2. Foundational: implementa a infraestrutura que desbloqueia as histórias.
  3. User stories: constrói e valida cada entrega de usuário na ordem definida.
  4. Polish: executa documentação, limpeza e validações transversais.

Em uma feature pequena, execute tudo de uma vez. Em uma feature grande, peça uma fase por vez:

/speckit-implement Implement only the Setup and Foundational phases. Stop before the user stories.

Depois de cada fase, confirme que os testes e as verificações passaram antes de avançar.

4. O que acontece quando há um erro

Uma tarefa sequencial que falha bloqueia as seguintes, porque continuar poderia produzir código apoiado em uma base incompleta. O erro deve ser reportado com contexto, e a causa deve ser corrigida antes de retomar.

Tarefas marcadas com [P] podem ser executadas em paralelo quando não compartilham dependências ou arquivos. Uma falha paralela não deve ser escondida: registre-a e valide o que conseguiu terminar.

5. Marque o trabalho concluído

Quando uma tarefa realmente terminar e tiver sido validada, ela deve ser marcada como concluída em tasks.md. A marca não significa apenas “o código foi escrito”; significa que a tarefa e suas verificações foram executadas.

Ao final, confira se:

  • todas as tarefas esperadas foram executadas;
  • os testes e comandos de validação passaram;
  • a implementação segue a especificação e o plano;
  • as tarefas concluídas estão marcadas corretamente.

Essa verificação prepara o próximo comando: converge compara a implementação com os artefatos e procura o que ainda ficou de fora.

6. Pratique: quando parar?

Uma tarefa fundacional falhou, mas duas tarefas de uma história posterior parecem independentes. O agente deve continuar?

Não. A fase fundacional bloqueia as histórias. Corrija a falha, valide a fundação e só então continue; independência paralela não elimina uma dependência de fase.
