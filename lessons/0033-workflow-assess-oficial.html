Lição 33 · 12 minutos · Workflow first-party

assess: decidir antes de especificar

Vitória de hoje: separar o veredito sobre uma ideia da aprovação humana do gate e fazer handoff para SDD só quando fizer sentido.

A pergunta deste fluxo

assess responde “há evidência para investir nesta ideia?”; não responde “como implementar?”. Pode ser usado num projeto Spec Kit vazio, pois avalia a ideia e escreve apenas artefatos de assessment. Uma ideia rejeitada com boa justificativa também é um resultado útil.

Inputs e pré-requisitos

O workflow requer Spec Kit >=0.9.0 e a extensão oficial opt-in assess, que fornece seus cinco comandos.

InputObrigatório?Uso
ideaSimIdeia em texto, URL, ticket ou apontamento para código existente.
slugSimNome curto em kebab-case para a pasta da ideia, por exemplo offline-sync.
integrationNãoPadrão auto; pode ser explicitado como copilot.
 
specify extension add assess
specify workflow run assess \
  --input idea="Permitir trabalhar offline e sincronizar ao reconectar" \
  --input slug=offline-sync \
  --input integration=copilot

Pipeline e artefatos

  1. intake → intake.md: captura e normaliza a ideia bruta.
  2. research → research.md: procura evidências a favor e contra, com origem/confiança.
  3. define → problem.md: define usuários, problema, objetivos, não-objetivos, métricas e custo de inação.
  4. shape → concept.md: compara opções conceituais, apetite e trade-offs.
  5. decide → decision.md: registra scorecard, justificativa, veredito e possível handoff.
  6. review-verdict: gate humano final com approve/reject; workflow para aqui.

Todos os arquivos ficam sob .specify/assessments/<slug>/. As etapas são chamadas sequencialmente pelo workflow, embora os comandos da extensão admitam alguns usos diretos: define pode trabalhar sem intake/research; shape requer problem.md; um go defensável precisa de conceito e evidência adequada.

Dois tipos diferentes de decisão

CamadaValoresO que significa
Veredito de ideia em decision.mdgo, needs-clarification, killConclusão sobre mérito/evidência da ideia.
Gate review-verdictapprove, rejectDecisão humana sobre continuar/encerrar a execução do workflow.

Approve não quer dizer go. Ele não altera o texto de decision.md, não recalcula o scorecard e não inicia specify. Se o veredito for needs-clarification, refine os artefatos com informação confirmada e revise decision.md; não regenere toda a pipeline por reflexo. Se for kill, registre a decisão e pare. Se for go, a passagem para SDD é manual e deliberada.

Reject no gate final segue on_reject: abort: termina esta execução. Não apaga os relatórios nem converte o veredito em kill. Quando o gate deixou o run pausado, use workflow status e workflow resume <run_id> para decidir o gate da mesma execução; após rejeitar, não há retry automático configurado.

Exemplo de handoff

Para “offline sync”, suponha que a decisão conclua go. Leia decision.md e decida se quer transformar o resumo em uma especificação. Só então invoque specify à parte:

/speckit-specify Use o handoff aprovado em .specify/assessments/offline-sync/decision.md para especificar a funcionalidade de trabalho offline.

Se o resultado for needs-clarification, complete os desconhecidos nomeados nos artefatos, preserve as fontes e atualize a decisão dependente. Se for kill, o processo de discovery termina sem abrir uma feature. Nenhuma dessas decisões faz o workflow automaticamente iniciar a próxima etapa.

Prática: o gate pode mudar o veredito?

decision.md recomenda kill. No gate final, alguém escolhe approve. O que acontece?
