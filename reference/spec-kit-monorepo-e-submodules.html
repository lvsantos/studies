Monorepo ou submodules?

Para uma feature coordenada entre submodules, mantenha um projeto Spec Kit no pai e um só ciclo de artefatos.

AspectoMonorepoRepos com submodules
Projeto Spec KitCada projeto isolado possui seu .specify/, constituição e specs/.Para uma feature transversal, somente o pai precisa do .specify/ e dos artefatos da feature.
ConstitutionsConstituições locais por projeto; sem herança embutida.Constitution transversal no pai; arquivo local mantido por cada repo filho e lido explicitamente.
GitUm Git raiz significa branches compartilhados entre projetos.Históricos e branches independentes; o pai registra um commit do submodule (gitlink).
ContratoReferencie a mesma fonte autoritativa entre os projetos.Publique versão ou mantenha cópia somente leitura com fonte e revisão imutável.
CoordenaçãoUse specs locais se os projetos tiverem ciclos independentes.Uma spec/plan/tasks/implement pode coordenar a feature completa; commits e checks continuam por repo.

Monorepo

repo/
  apps/web/.specify/       apps/web/specs/
  apps/api/.specify/       apps/api/specs/
  packages/ui/.specify/    packages/ui/specs/
  • Execute slash commands dentro do projeto para resolver o .specify/ mais próximo.
  • Para scripts/CI, SPECIFY_INIT_DIR deve apontar para diretório existente que contenha .specify/; valide o destino.
  • Constituições são locais; não há herança embutida de uma constituição comum.

Repos independentes com submodules

produto/
  .specify/memory/constitution.md   # regras transversais + instrução para ler as locais
  specs/023-feature/{spec,plan,tasks}.md
  modules/api/CONSTITUTION.md       # fonte local, versionada no repo api
  modules/web/CONSTITUTION.md       # fonte local, versionada no repo web
  1. Inicialize Spec Kit somente no pai e mantenha nele um único diretório da feature com spec.md, plan.md e tasks.md.
  2. Use a constitution do pai para regras transversais e mande o agente ler as constitutions locais dos repos alterados. Spec Kit não as descobre nem combina automaticamente.
  3. Em plan.md/tasks.md, mapeie tarefa → repo → constitution local → checks; inclua contratos e validação de integração.
  4. Mantenha a constitution local dentro do repo dono (por exemplo, CONSTITUTION.md) e aprove alterações com seus responsáveis.
  5. O gitlink do pai fixa o commit do submodule e, portanto, a revisão da constitution que o workspace consulta. Mudanças de código continuam sendo commits separados.
git clone --recurse-submodules URL
git submodule update --init --recursive

Não confunda

  • O ciclo único é adequado quando existe uma feature coordenada; projetos com roadmaps independentes ainda podem manter Spec Kits separados.
  • Git submodules não juntam históricos: a execução única do agente não vira commit atômico entre repos.
  • Constitution local fora do contexto não será automaticamente aplicada; explicite o caminho e confirme a leitura.
  • Não duplique a constitution local na do pai: isso cria cópias concorrentes e drift.
