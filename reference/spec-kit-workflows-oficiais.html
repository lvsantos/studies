Três workflows, três perguntas

Escolha pela natureza do trabalho, não pelo nome do comando.

WorkflowPerguntaInputs exigidosDependências
speckitComo entregar uma feature aprovada?spec; integration opcional, padrão auto.Spec Kit >=0.8.5; comandos core.
bugfixComo diagnosticar, corrigir e verificar comportamento quebrado?report e slug; integration opcional.Spec Kit >=0.9.0; extensão bug.
assessVale investir nesta ideia?idea e slug; integration opcional.Spec Kit >=0.9.0; extensão assess.

Ordem, saídas e gates

speckit: specify → review-spec → plan → review-plan → tasks → implement
bugfix:  assess → review-assessment → fix → test
assess:  intake → research → define → shape → decide → review-verdict
  • speckit: dois gates com opções approve/reject; rejeição usa on_reject: abort.
  • bugfix: um gate entre diagnóstico e alteração de código; somente fix edita fonte. Resultado de teste: verified, partial ou failed.
  • assess: um gate depois da decisão; veredito em decision.md: go, needs-clarification ou kill. Handoff para specify é manual.

Gate, run e veredito

approve/reject são opções de gate. Não são sinônimos dos vereditos de assessment, nem dos resultados de verificação de bug. Um run pode estar completed enquanto um artefato de domínio pede atenção; leia sempre test.md ou decision.md.

Quando a execução pausa, consulte e retome o mesmo run_id:

specify workflow status
specify workflow status <run_id>
specify workflow resume <run_id>

O workflow armazena execução em .specify/workflows/runs/<run_id>/. Os gates first-party descritos aqui não configuram um loop de edição; reject aborta a execução e não apaga artefatos já escritos.
