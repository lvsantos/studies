O que fazer com artefatos de uma feature concluída

Duas perguntas independentes, três modelos de mutação, e como isso se encaixa nos três níveis de "spec-driven development".

Duas perguntas separadas

1. Por quanto tempo a spec importa?
Pergunta sobre o ciclo de vida geral do método (níveis de SDD, ver abaixo).
2. O que acontece com spec.md, plan.md e tasks.md quando os requisitos mudam?
Pergunta sobre a estratégia de mutação dos artefatos dentro do Spec Kit — os três modelos de persistência.

Os três níveis de SDD (Birgitta Böckeler, Martin Fowler)

NívelO que significaO que acontece com a spec após a feature
Spec-firstEscreve-se a spec antes de codificar.Pode ser descartada; não existe compromisso de mantê-la.
Spec-anchoredA spec continua existindo depois da implementação.Usada para evoluir e manter a feature no futuro.
Spec-as-sourceA spec é a única fonte editada por humanos.Código é gerado/regenerado a partir dela; humano não toca no código.

Fonte: Understanding Spec-Driven-Development: Kiro, spec-kit, and Tessl. O artigo observa que o Spec Kit cria uma pasta por spec e um branch por mudança — o que aponta mais para "spec-first" por padrão, a menos que a equipe adote deliberadamente uma disciplina de manutenção.

Os três modelos de persistência do Spec Kit

ModeloRegra de mutaçãoVantagensDesvantagens
Flow-back spec Edita-se qualquer artefato primeiro (spec, plan, tasks ou o próprio código) e depois se reconcilia o conjunto. Iteração rápida; aproveita descobertas feitas durante a implementação; bom para times pequenos e próximos. Risco de divergência silenciosa: se ninguém devolve a descoberta para spec.md, futuros colaboradores não sabem em qual artefato confiar.
Flow-forward spec Artefatos concluídos são imutáveis. Uma mudança de requisito cria uma nova pasta de feature em vez de alterar a antiga. Trilha de auditoria clara; cada pasta é um registro histórico; fácil explicar como o projeto chegou onde está. Duplicação: decisões relacionadas ficam espalhadas em várias pastas; exige convenção de nomes e links para manter a linhagem legível.
Living spec spec.md é o contrato. Edita-se a spec primeiro, depois se regenera ou revisa plan.md e tasks.md a partir dela. Consistência forte entre requisito e implementação; spec.md como fonte única de verdade. Risco de perder racional de implementação valioso se os artefatos derivados forem descartados sem preservar decisões importantes em outro lugar.

Correlação entre os dois eixos

Modelo de persistênciaNível de SDD que ele tende a realizar
Flow-back, sem disciplina de reconciliaçãoNa prática vira spec-first: o arquivo existe, mas ninguém confia nele.
Flow-back, com reconciliação disciplinadaSpec-anchored: a spec continua confiável porque é atualizada a cada descoberta.
Flow-forwardSpec-anchored por feature, não por capacidade: cada pasta é um âncora histórico, mas decisões relacionadas se fragmentam entre pastas.
Living specA realização mais completa de spec-anchored; aproxima-se de spec-as-source para plan.md/tasks.md (que passam a ser derivados), mas o código em si ainda é editado por humanos — diferente de ferramentas como o Tessl.

Duas perguntas para decidir o modelo do seu time

  1. As pastas de feature concluídas devem ser registros históricos ou áreas de trabalho editáveis?
  2. spec.md é a única fonte de verdade, ou plan.md/tasks.md podem virar fontes co-iguais?

O modelo é uma convenção de time, não uma flag de CLI. Depois de decidir, documente a escolha na constitution do projeto ou nas notas de onboarding.
